# 2차 공유본 프론트엔드 통합 작업 지시서

## 1. 목표 및 우선순위
현재 메인 프로젝트는 1차 공유본을 반영하고 DB·API 계약과 기능 구조를 수정한 구현이다. 2차 공유본은 팀원이 별도로 발전시킨 UI·UX·IA·기능·사용자 플로우 참고 구현이다.

- **현재 메인의 DB·API·데이터 모델·백엔드 계약을 유지한다.** `docs/contracts/`가 확정 계약의 기준이다.
- **2차 공유본의 신규·개선 UI·UX·IA·기능 플로우를 적극적으로 통합한다.** 단, 기존 메인의 정상 동작을 보존한다.
- 공유본의 데이터 처리·연동 방식이 충돌하면 UI와 사용자 경험을 가져오되 현재 메인의 계약에 맞게 연결한다.
- 공유본을 통째로 덮어쓰지 않는다. 기존 기능 삭제나 계약 변경이 필요하면 먼저 사용자에게 확인한다.
- **우선순위: 기능 완성도 > 계약 정합성 > 코드 품질 > 토큰 절약.** 단순한 토큰 절약을 이유로 필요한 분석·구현·검증을 생략하지 않는다.

## 4. 통합 판단 및 구현 절차
1. 실제 실행되는 화면과 연결 관계를 기준으로 양쪽 UI·IA·사용자 플로우를 비교한다.
2. 기능 단위로 **동일 / 공유본에서 개선 / 공유본 신규 / 메인 전용 / 계약 충돌 / 중복·불필요**를 구분한다.
3. 동일 기능은 메인의 계약·연동을 유지하고 공유본의 개선된 표현·동선만 적용한다.
4. 개선·신규 기능은 가능한 범위에서 실제 화면 전환, 입력, 상태 변화, 조회·저장·확정 흐름까지 연결한다.
5. 공유본의 저장소·Mock·API 접근이 계약과 충돌하면 현재 메인의 서비스·어댑터에 연결한다. 계약에 없는 서버 기능을 임의로 만들거나 Mock을 실제 연동으로 가장하지 않는다.
6. 메인 전용 기능은 보존한다. 중복 기능은 사용자 경험과 계약을 기준으로 정리하되 임의 삭제하지 않는다.
7. 변경이 기존 아키텍처에 영향을 줄 때는 필요한 수준의 리팩터링을 허용하되, 무관한 재설계·포맷 변경은 하지 않는다.
8. 계약 변경, 기존 기능 제거, 해석이 불가능한 충돌은 사용자 확인을 요청한다. 그 외에는 장문 중간 보고 없이 진행한다.

## 5. 코드 탐색·품질 원칙
- 이미 확인된 디렉터리 구조와 파일 목록을 반복 탐색하지 않는다.
- 위 우선 후보에서 시작하지만 정확한 구현에 필요한 직접·간접 의존 파일은 자유롭게 확인한다.
- UI·IA·기능 플로우의 변경사항을 누락 없이 파악하고, 상태 관리·이벤트 처리·데이터 흐름·API 연결은 충분히 추적한다.
- 계약 문서는 관련 기능의 필요한 부분을 확인한다. 백엔드·DB 소스도 계약 충돌 확인에 필요하면 제한적으로 조회할 수 있다.
- 기본적으로 1차 공유본, `node_modules/`, `dist/`, `.git/`, 무관한 `backend/`, `infra/`, `renderer/`, `data/`와 테스트·배포 파일을 탐색하지 않는다. **필요한 의존성 확인까지 금지하는 의미는 아니다.**
- 파일 전체 출력·전체 프로젝트 재탐색·중복 분석·장황한 중간 보고를 줄인다. 품질에 필요한 탐색은 생략하지 않는다.

## 6. Git 버전 전략 — 작업 시작 전에 수행
1. 현재 브랜치, 작업 트리 상태, 원격 연결을 확인한다.
2. 현재 메인 상태를 안전하게 보존할 체크포인트 커밋을 만든다: `chore: checkpoint before second handoff integration`. 기존 미추적 파일을 무조건 `git add .` 하지 말고 포함 대상을 확인한다. `.env`, 비밀정보, 빌드 산출물 등은 커밋하지 않는다. 이미 추적 중인 민감 파일이 있으면 중단하고 보고한다.
3. 사용자가 말한 `main`이 실제 기준 브랜치인지 확인한다. 기존 작업물이 다른 브랜치나 미커밋 상태에 있으면 임의로 전환·폐기하지 말고 확인한다.
4. 체크포인트가 보존된 현재 기준에서 `dev` 브랜치를 생성·체크아웃한다. `dev`가 이미 있으면 덮어쓰거나 초기화하지 말고 상태를 보고한다.
5. 모든 통합 수정과 기능별 Conventional Commits는 `dev`에서 수행한다. 작업 중 `main` 직접 수정, 원격 푸시, 배포는 금지한다.

## 7. 위험도 기반 검증
**필수**
- 프론트엔드 빌드 및 변경 파일의 문법·import·타입 오류 확인
- 변경 기능의 주요 사용자 플로우 확인
- 현재 DB·API 계약과의 정합성 확인
- 신규·기존 기능 간 상태 충돌 확인
- 변경 영향권에 있는 기존 기능의 회귀 확인

**필요할 때만**
- 복잡한 상태 전이·저장·확정 로직의 단위 테스트
- 여러 화면을 관통하는 통합 테스트
- 오류 수정 후 관련 범위 재검증

**기본 생략**
- 변경 범위와 무관한 전체 테스트 스위트
- 같은 조건의 반복 E2E·브라우저 자동화
- 무관한 리팩터링·포맷 수정·테스트 대량 추가

빌드 1회를 기본으로 하되 수정·실패 시 필요한 재실행을 허용한다. 실제로 수행하지 않은 검증은 성공으로 보고하지 않는다. **검증 깊이는 위험도에 따라 정하며 품질을 희생하지 않는다.**

## 8. 완료·로컬 QA·병합
1. 통합 변경을 `dev`에 커밋하고 `dev` 체크아웃 상태를 유지한다.
2. 사용자가 로컬에서 실행할 정확한 명령과 접속 주소를 제공한다. 실행 환경·선행 조건이 있다면 함께 밝힌다.
3. 신규·개선 UI·기능, 보존된 메인 기능, 미반영·미검증 항목과 잔여 위험을 간결하게 보고한다.
4. 사용자가 직접 로컬 QA를 진행하고 피드백을 주면 `dev`에서 수정·커밋한다.
5. **사용자가 명시적으로 최종 승인하기 전까지 `main` 병합·원격 푸시·배포 금지.** 승인 후 `dev`를 `main`에 병합하고 결과를 확인한 뒤 원격 `main`에 푸시한다. 충돌이나 예상 외 배포 설정은 보고한다.
