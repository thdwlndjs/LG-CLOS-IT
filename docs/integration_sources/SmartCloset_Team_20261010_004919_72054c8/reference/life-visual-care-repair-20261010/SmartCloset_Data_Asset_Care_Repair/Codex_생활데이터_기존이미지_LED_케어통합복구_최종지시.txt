0. 이번 작업의 한 문장 목표
새 생활 데이터의 옷과 이력을, 이미 사진과 위치 안내가 작동하던 의류 자산에 명시적으로 대응시켜,
마이 → 옷장 → 같은 옷의 사진·LED·이력·관리법 → 코디·달력 재조회가 하나로 이어지게 복구한다.
이번 작업은 새 의류팩 생성이나 원격 DB 연결이 아니라 '두 데이터 묶음의 결합 누락과 표시 오류'를 고치는 작업이다.
기존 기능을 없애거나 빈 사진/위치를 정상 상태로 받아들이고 종료하지 마라.

- PDF·원본 옷장 사진·LED OFF 배경·원래 의류팩과 생활 데이터팩은 보존한다. 앱 통합용 파생 매핑·변환 코드만 변경한다.
- 현재의 카드·초안·사용자가 추가한 기록을 보존한다. localStorage/IndexedDB 전체 삭제, 시드 재초기화, 이전 commit으로 reset/checkout하지 않는다.
- 최근 사용자 요구가 과거 '사진은 나중에, 없는 상태로 진행' 지시보다 우선한다. 연결 가능한 기존 사진과 시연 LED는 이번에 실제로 복구한다.
- 다만 '기존 사진 재사용'은 실제 브랜드 상품과의 동일성 인증이 아니다. 시연용 시각 자료·실제 제품 근거·실물 위치를 섞지 않는다.

4. 결합 방식 — 기존 자산과 새 이력을 같은 의류에 붙인다
4.1 기본 전략
현재 생활 프로필에 이미 생성된 안정된 의류 ID를 가급적 유지한다.
그 ID를 기준으로 사진/시연 위치를 보강하고, 새 생활 이력·코디·달력·취향은 그대로 연결한다.
기존 이미지가 있는 프로필로 돌아가 새 이력을 포기하는 방식은 복구가 아니다.
옛 48벌과 새 32벌을 무조건 합쳐 80벌로 만드는 것도 아니다.

4.2 명시적 대응표
현재 모델을 재사용해 다음 의미를 가진 프로젝트 내부 매핑을 작성하라. 이 이름으로 새 DB 테이블을 강제하지 않는다.
- sourceDataset + sourceProfileRef + sourceGarmentRef
- currentLocalProfileId + currentCanonicalGarmentId
- legacyCatalogDataset + legacyCatalogRef + 검증한 legacyAssetId/hash/version
- 실제 renderer가 해석하는 catalog 표시 자산(기존 투명 파생본 우선)
- scenePlacement의 출처·버전, slotId, ledAnchorId 또는 미확정 사유
- imageBindingKind: 동일한 시연 항목의 자산 재사용 / 명시된 예시 이미지 / 아직 미확정
- productIdentity: 실제 제품·변형 확인 / 시연에 지정한 상품 / 외형 참고만 / 미확정
- careApplicability: 그 옷에 적용 가능 / 시연 상품 참고 / 일치 미확인 / 근거 부족
- 결정 근거와 남은 검수
사진 연결, LED 연결, 상품/케어 동일성은 각각 별도 필드로 검토한다.
사진을 찾았다는 사실이 SKU 확인·정확한 소재·위치 관측·피팅 성공을 의미하지 않는다.

4.3 연결 방법
1) 기존 명시된 같은 항목 관계가 있으면 재사용한다.
2) 없다면 기존 파일을 열어 종류·색·형태·길이·디테일을 대조한다.
3) 충분히 맞는 생성 시연 이미지의 재사용은 이번 사용자 요청 범위에 포함된다.
   단, 실제 상품 사진으로 표시하지 않고 단독 이미지 복구용 시연 참조임을 유지한다.
4) 실루엣/색/종류가 다른 자료는 자동 확정하지 않는다. 검은 티셔츠에 네이비 티셔츠, 블라우스에 롱슬리브,
   데님에 정장바지, 신발에 셔츠를 붙여 수량을 맞추지 않는다.
5) 비슷한 후보만 있으면 해당 항목의 구체적 차이를 기록한다. 대응 가능한 나머지 의류와 화면은 계속 복구한다.
   모든 32벌을 미연결로 방치하거나 매 항목 사용자에게 질문하고 전체를 멈추지 않는다.
6) 이름만 비교하는 fuzzy matching은 후보 탐색에만 사용한다. 배열 순서·같은 raw ID·첫 이미지 fallback으로 실행하지 않는다.
7) 새 의류를 기존 시연 의류로 아예 변경하는 것은 표시 자산 재사용과 다른 변경이다.
   이 경우 원래 상품 설정과 품목이 달라질 수 있으므로 별도 변경안으로 두고 몰래 이름/brand/product_ref를 바꾸지 않는다.

4.4 null은 삭제 명령이 아니다
일부 레코드를 보강할 때 입력의 null/미제공이 기존의 유효한 이미지·시연 위치·수동값을 지우지 못하게 하라.
- asset 미제공: 기존 검토된 연결 유지
- explicit clear: 사용자가 명확히 실행한 제거 동작에서만 처리
- 충돌: 원본 보존 후 충돌 표기, 임의 우선순위로 덮지 않음
조건 없는 {...old, ...incoming} 덮어쓰기나 import 시작 시 전체 목록 교체를 피한다.
다만 실제로 다른 옷의 연결을 '빈 값 방지'라는 이유로 유지해서도 안 된다. 같은 canonical 항목 검사가 먼저다.

5. 동봉 후보표를 사용하는 법
mapping_candidates.review.json은 옛 원본과 새 계획을 대조한 후보이며 현재 앱의 실제 ID/경로/위치를 담지 않는다.
- STRONG_DEMO_VISUAL_CANDIDATE: 우선 실제 파일·사용권·프로필·현재 renderer와 대조 후 연결.
- ILLUSTRATION_REVIEW: 형태는 참고 가능하나 실제 상품의 동일 사진은 아님. 명시적 예시 표시/상품 적용 범위를 구분.
- CONFLICT_REVIEW: 색·길이·종류가 다를 수 있으므로 자동 적용 금지.
- NO_COMPATIBLE_CANDIDATE: 이 아카이브에서 적합한 자료를 못 찾은 것. 최신 앱의 추가 자산을 찾아볼 수 있다.

확실도가 높은 시연 후보 예:
PSU S04(그레이 맨투맨) → legacy T07
PSU S09 / PHW H09(베이지 치노) → legacy B02
PSU S12 / PHW H13(베이지 트렌치) → legacy O01
PHW H07(크림 케이블 니트) → legacy T05
PHW H10(인디고 데님) → legacy B03
PHW H15(브라운 앵클부츠) → legacy S04
PHW H16(블랙 백팩) → legacy A05
PSU S15(화이트 스니커즈) → legacy S01
이것은 같은 실물이라는 인증이 아니라 기존 생성된 시연 자산의 대응 후보다.

PSU S01(베이지 포플린)과 legacy T02(아이보리·린넨풍 셔츠)는 동일 상품으로 확인된 바 없다.
legacy T01을 쓰는 화이트 셔츠도 COS 제품 사진으로 검증된 자료는 아니다.
상품 사실을 유지한 시연에 예시 사진을 쓰려면 작은 '예시 이미지' 구분과 상품 근거의 적용 범위를 명시하라.
예시 사용으로 실제 브랜드·라벨 검증 상태를 올리지 않는다.

6. 프로필과 원본 자산의 소유 범위
- 같은 생성 의류 이미지를 두 시연 프로필이 허용된 공통 자산으로 참조할 수는 있다.
  이 경우 의류 ID·착용 이력·선택·코디·초안은 서로 다른 프로필에 남는다.
- 공유 파일 참조와 같은 실물 의류를 구분한다. 두 개의 그림이 같다고 두 가족의 의류/이력을 합치지 않는다.
- 실제 개인 사진/비공개 자산은 파일 hash가 같다는 이유로 다른 사용자에게 공개하지 않는다.
- 새 프로필로 전환했을 때 이미지와 LED가 옛 활성 프로필의 값을 재사용하지 않게 resolver key와 cache를 분리한다.
- 고객이 '옛 이미지팩 프로필'과 '새 생활 프로필'을 번갈아 눌러야 사진과 이력을 따로 볼 수 있는 구조는 실패다.

7. LED 복구 — 옛 원본의 location null과 실제 시연 배치를 혼동하지 않는다
- 과거 앱에서 정상 점등하던 장면 배치/앵커/의류 연결을 현재 코드와 이전 검증된 캡처에서 확인한다.
- 새 canonical 의류에서 legacyCatalogRef를 거쳐 검토된 scenePlacement를 찾도록 기존 resolver에 연결한다.
- 물리 위치(location observation)와 이미지상의 시연 위치(scene placement)를 별도 경로로 유지한다.
  physical_location이 null이라는 이유만으로 검증된 demo scenePlacement까지 버리면 안 된다.
- 이미 정확하게 맞춘 LED 좌표를 보존한다. 사진 좌표와 같은 contain 변환을 사용한다.
- 의류 선택 → 같은 옷 사진·이름·LED. 케어 하위 탭 전환에서도 유지.
- 다른 옷 선택 → 이전 안내 정리 후 새 옷 위치만 표시. 빈 매핑에서 옛 LED를 남기지 않는다.
- '이 옷으로 입기' → 최종 선택 조합의 보유옷만, 알려진 시연 위치를 중복 제거해 점등.
- 외부 상품에 LED를 켜지 않는다. 위치 미확정은 짧게 구분한다.
- 같은 선반을 실제로 공유하는 여러 의류는 하나의 LED를 쓸 수 있다.
- 새 프로필의 동일 이미지라는 이유만으로 다른 가족의 실물 위치를 그대로 복사하지 않는다.
  기존 시연 배치를 참조하는 것은 이번 로컬 시연용 시각 연결임을 기록한다.
- 매핑이 복구된 화면에 '위치 확인 필요'와 '이 옷의 위치는 아직 확인되지 않았어요'가 중복으로 남아 있으면 안 된다.
  '오른쪽 선반 · 시연 위치'처럼 실제로 제공하는 정밀도에 맞는 안내를 사용한다.
- 실제 센서 관측/옷 인출 완료/이동 사건을 생성하지 않는다.

8. 케어 텍스트 정상화 — 조사 메모와 관리 안내를 구분한다
현재 보이는 문제:
영문 발췌 + sources.notes/products.issues + 조사 실패 기록 + 긴 URL이 고객 본문 하나로 붙어 있다.
이것은 관리법의 정확성 문제 이전에 데이터 역할이 잘못 연결된 문제다.

8.1 유지할 층
A. 출처 원문: 원문 언어 그대로, 필요한 근거 보기에서 확인 가능하게 보존.
B. 검토된 관리 항목: 해당 상품·의류와 적용 범위 및 근거 문장이 연결된 구조화 값.
C. 고객 표시: 짧은 한국어 요약·확인된 출처·필요한 불확실성 안내.
D. 연구/개발 기록: notes/issues/검색 실패/파싱 상태/내부 ref/수집 한계. 내부 검토에 보존하되 고객 본문과 모델의 관리 근거에 섞지 않는다.

8.2 allowlist view-model
기존 선택기/DTO에 맞춰 고객용 care view-model을 구성한다. 새 전체 관리 플랫폼을 만들지 않는다.
기본 화면에 허용하는 의미:
- 현재 canonical 의류와 사진
- sourceKind(실물 라벨/공식 상품 안내/시연 참고)
- verificationState와 해당 의류 적용 여부
- evidence-linked care rows의 한국어 설명
- 부족한 정보 한 문장
- '근거 원문'으로 원문과 도메인/출처 확인 가능
notes/issues/raw concatenation을 기본 본문에 넘기지 않는다.
문장에서 'open' 등 특정 단어만 지우는 정규식 땜질로 해결하지 말고, 데이터 입력 경로 자체를 분리한다.
긴 URL을 기본 본문에 쓰거나 source_ref/검색 도구 번호를 사용자 설명에 섞지 않는다.
근거 보기에서도 실제 발췌와 검증 상태만 읽기 좋게 보여주고 내부 작업 일지를 원문이라고 부르지 않는다.

8.3 번역/표시의 정확성
같은 상품의 검토된 원문이 존재할 때에만 다음처럼 표시한다.
- Wash at or below 40°C → '40°C 이하에서 세탁'
- Line dry → '걸어서 건조'
- Do not dry clean → '드라이클리닝 금지'
'Line dry'를 '그늘 건조' 또는 '건조기 금지'로 확대하지 않는다.
'cool'을 30/40도로 임의 환산하지 않는다.
원문에 없는 표백·온도·다림질·텀블건조 조건은 추가하지 않는다.
허용이 불명인 것과 명시적 금지는 별도다. 직접 번역/기존 구조화값 표시에는 새 유료 모델 호출이 필요하지 않다.

8.4 P04(베이지 포플린) 특별 점검
이 준비팩의 P04/SRC-P04는 official_search_snapshot이며 원문 페이지 재확인 전이다.
'공식 상품 관리 안내'라는 큰 제목만으로 검토 완료된 정상 지침처럼 올리지 않는다.
- 현재 고객 표시는 '관리 정보 원문 확인이 필요해요' 등 짧은 확인 필요 상태.
- 저장된 발췌 번역을 열어볼 수는 있지만 '검색에서 확보한 상품 안내 발췌 · 원문 재확인 전'임을 구분한다.
- 구조화 데이터의 다림질 high·표백 조건은 동봉 short_excerpt에 근거가 드러나지 않는다.
  별도의 동일 상품 원문 근거를 확보해 검토한 사실이 없으면 확정 관리 행으로 노출하지 않는다.
- products.issues를 삭제하거나 검증 상태만 verified로 바꾸어 경고를 없애지 않는다.
- 현재 요청은 새 크롤링/웹수집 작업이 아니다. 이미 확보된 근거로 가능한 범위에서 바로잡고,
  신규 원문 확보가 필요한 항목만 자료 보완으로 남긴다.

8.5 이미지 연결과 케어 적용의 독립성
생성된 '화이트 셔츠' 이미지에 실제 COS의 관리법을 같은 실물의 라벨처럼 붙이지 않는다.
1) 실제 동일 제품/변형 근거가 확인됨: 그 범위에서 공식 안내 적용 가능.
2) 로컬 시연에서 특정 상품을 지정하고 예시 그림을 사용: '시연에 설정한 상품 안내'/'예시 이미지'로 한계를 남긴다.
3) 외형 유사만 확인됨: 공식 자료는 별도 상품 참고로 보존하고 이 옷의 확정 세탁 지침으로 쓰지 않는다.
4) 실물 라벨 사진 없음: 가짜 라벨 아이콘/기호/사진 생성 금지. 공식 상품 안내를 실물 라벨로 표현하지 않는다.
무작정 모든 케어를 '없음'으로 비우는 것도 피한다. 검토된 같은 상품 근거가 있는 항목은 한국어로 유용하게 표시한다.
기존 AI 도움 함수에는 검증된 근거·현재 이력·적용 범위만 전달한다. 오염된 고객 문자열이나 notes를 재활용하지 않는다.

9. 이력 숫자는 보존하고 뜻을 명확히 한다
첨부 S01은 원팩 기준 총 기록 4회·4일 / 마지막 세탁 후 3회·3일이다. 서로 다른 집계이며 단순 불일치가 아니다.
- 대표 값: '지난 세탁 후 착용 3회 · 3일'
- 보조: '마지막 세탁 10월 4일', '마지막 착용 10월 8일'
- 전체 통계를 보여줄 때: '전체 기록된 착용 4일'처럼 범위를 명시.
현재 스크린샷의 4일을 무조건 3일로 고치는 방식 금지.
시연 기준시각을 사용해 사건에서 계산한다. 시계의 실시간과 시연 이력 기준을 조용히 섞지 않는다.
다림질은 세탁 기준을 초기화하지 않고, 선택/계획은 실착 일수에 더하지 않는다.
안내 열람·탭 이동·사진 연결 복구는 새 세탁/실착/이동 사건을 생성하지 않는다.
원문도 없고 사진도 없는 상태의 중복 경고가 화면을 채우지 않도록, 각 부족 항목을 한 번만 알린다.

10. 코디·홈·캘린더까지 같은 복구 결과를 사용한다
공통 의류 view-model/asset resolver를 쓰고 화면마다 별도 이름 기반 매칭을 두지 않는다.
- 옷장 격자 / 상세 / 케어 / 코디 후보 / 현재 슬롯 / 홈 카드 / 내 코디 / 날짜 카드 모두 같은 의류의 사진을 사용.
- 자료 연결이 갱신되면 그 자산을 쓰는 카드의 '표시용 캐시'만 필요한 범위에서 갱신.
- 과거 snapshot의 의류 선택·사건 의미·사용자가 정한 이름을 몰래 수정하지 않는다.
- 사진 미연결 때 만든 빈 합성 카드가 영구 캐시로 남지 않도록 presentation revision과 의존 자산을 추적.
- 이미 저장된 카드의 이미지 파생 재생성은 기존 단품으로 일반 렌더링한다. 새 AI 카드 이미지 생성 금지.
- 사진이 보인다고 피팅 성공으로 표시하지 않는다. 원본 LOOK01~03 준비 결과는 사람·전체 조합·자산 버전이 정확히 맞을 때만 사용.
  legacy ID alias 추가를 이유로 결과 매칭 조건을 느슨하게 하거나 대표 인물을 모든 프로필에 복사하지 않는다.
- 피팅 입력·원격 결과·비용 상태는 이번에 변경하지 않는다. 일반 카드가 복구돼도 live 미검증은 그대로다.

11. 데이터 보정은 한 번 적용되고 다시 해도 안전해야 한다
- 변경 전에 현재 local profile 데이터/카드/사건/초안/원래 asset map을 로컬 백업에 보존한다.
- 현재 저장 엔진의 트랜잭션/일관된 전체 스냅샷 방식으로 binding과 참조를 함께 적용한다.
  localStorage이면 새 세대의 완성 스냅샷을 검증 후 전환하는 등 기존 엔진에 맞는 최소 원자성 확보.
- 새 전역 store나 원격 schema를 만들지 않는다.
- 같은 repair version+source hash를 재적용하면 동일 결과. 첫 복구 이후 사용자가 새로 쓴 값을 시드로 되돌리지 않는다.
- 변경/보존/미연결 숫자를 기록하되 로컬 사용자 수정 자료를 검수 보고서에 과도하게 노출하지 않는다.
- 오류 시 현재 새 이력은 보존하고 이전 유효 binding으로 복구한다. 어느 쪽 자료 전체를 삭제하지 않는다.
- 데이터 로딩 중 placeholder를 한 번 표시한 뒤 영구히 캐시하지 않는다. binding 준비 완료 시 모든 구독 화면 갱신.
- 실제 이미지 요청의 성공뿐 아니라 naturalWidth/decode/알파 표시를 확인한다. HTTP 200만으로 사진 복구 합격이라 하지 않는다.
- 이미지 연결에 성공해도 잘못된 상품·소유자·위치면 실패다.

12. UI와 시나리오 완료 기준
투명 배경, 현재 글자 크기/조작 위치 개선, 가로 탐색을 유지한다. 사진을 채운다고 큰 흰 패널을 다시 만들지 않는다.
김수진: 프로필 → 격자에서 사진으로 옷 선택 → 그 옷의 LED → 같은 옷 이력 → 읽기 쉬운 관리 안내/근거 → 같은 위치 안내.
최휘재: 프로필 → 홈의 구성형 카드에 사진 → 같은 카드 → 상의 교체 → 구성형 저장/오늘 선택 → 보유옷 LED → 날짜 카드에도 같은 사진.
수진과 휘재의 생활 프로필 안에서 모두 확인한다. 옛 이미지팩 프로필의 캡처를 대신 제출하지 않는다.
동봉 화면에서 비어 있던 대표 항목과, 명확히 대응 가능한 여러 종류를 실제로 눌러 비교하라.
진짜 자료가 없는 항목은 개별 대기로 남겨도 되지만, 매핑 가능한 항목까지 일괄 미연결로 남기고 완료 보고하지 마라.

13. 수용시험 — PASS/FAIL/NOT_RUN/진짜 자료대기 구분
R01 현재 생활 프로필과 기존 데이터 모두 보존, 초기화·삭제 없음.
R02 life S01(셔츠)와 legacy S01(스니커즈)의 원본번호 충돌을 오연결하지 않음.
R03 life H01(셔츠)와 legacy H01(모자)도 동일 번호로 조인하지 않음.
R04 실제 검토한 자산 연결 후 의류 격자·상세의 이미지 decode 성공 및 종류/색 일치.
R05 같은 옷의 케어·코디 후보·홈·날짜 카드에서 동일 자산 사용.
R06 이미 투명한 원본/파생본을 사용하며 흰 박스·의류 훼손 없음.
R07 새 metadata의 null이 기존 유효 사진/시연 위치/수동값을 지우지 않음.
R08 explicit clear와 미제공이 구분되고, 실제 다른 옷의 자산은 승계하지 않음.
R09 새 canonical ID → legacy visual ref → 기존 검토 scenePlacement → 같은 LED 연결.
R10 physical_location null이어도 유효한 demo scenePlacement는 시연 위치로 안내.
R11 위치가 정말 없는 옷/외부 상품에는 LED 없음; 직전 옷의 LED 잔존 없음.
R12 같은 선반 공유·옷/코디 전환·프로필 전환·resize에서 잘못된 점등 없음.
R13 PSU·PHW의 의류·이력 분리; 공용 시연 이미지 참조가 소유권 병합을 만들지 않음.
R14 이름/슬롯/색 충돌 후보는 자동 확정되지 않음.
R15 고객 케어 본문에 notes/issues/직접 open/파싱/내부 ref/긴 URL 미노출.
R16 내부 조사 기록은 원본으로 남고, 검증 상태와 사용자에게 필요한 주의는 숨기지 않음.
R17 구조화된 관리값마다 실제 근거와 적용 범위 연결; 번역이 원문 조건을 확대하지 않음.
R18 official_search_snapshot은 verified physical label/검토 완료 안내로 승격되지 않음.
R19 P04 철/표백 등 발췌로 뒷받침되지 않는 항목을 확정 지침으로 노출하지 않음.
R20 생성 이미지 사용만으로 실제 브랜드·섬유·상품 동일성을 확정하지 않음.
R21 이력 4일 전체/세탁 후 3회·3일 의미 보존; 다림질/계획이 실착 계산을 바꾸지 않음.
R22 화면을 열고 사진을 복구해도 의류 수·실착·세탁·이동 사건이 무단 증가하지 않음.
R23 연결 후 빈 카드 파생 캐시가 갱신되며 과거 snapshot의 조합 의미는 보존.
R24 동일 repair 재실행/새로고침/서버 재시작/프로필 왕복 후 연결·카드·사용자 수정 유지.
R25 기존 피팅의 전체 조합·인물·버전 일치 검사를 우회하지 않음.
R26 수진의 같은 옷 사진+이력+케어+LED 실제 브라우저 녹화 확보.
R27 휘재의 홈+조합+선택+LED+달력 같은 사진 재조회 녹화 확보.
R28 진짜 누락 자산 목록은 항목별 원인/현재 후보/해결 필요만 보고, 검사 통과 수에 합산하지 않음.
R29 로그인·외부API·원격DB·새 팩 생성 없이 로컬 작업 수행.
R30 타입/빌드/단위검사와 실제 UI·매핑·상품근거 검증을 분리해서 보고.

14. 실행과 보고
- 새 설계 문서를 길게 쓰는 대신 현재 코드에서 원인을 확인하고 대응표 작성 → 대표 항목 1개 복구 → 전체 가능한 항목 확대 → 회귀검사.
- 완성된 대표 항목을 직접 브라우저로 열어 사진+이력+LED가 같은 화면 흐름에 있는지 확인한 뒤 나머지에 적용.
- 자료 부족 한 항목 때문에 전체를 대기하지 않고, 외형이 비슷하다는 이유만으로 잘못된 정보까지 합치지 않는다.
- 작은 구현 결정은 현재 구조에 맞춰 진행한다. 새 비용/운영DB/실물 변경은 하지 않는다.
- 기능별 관련 파일만 commit한다. 실제 원격이 있고 기존 승인된 안전한 작업 브랜치일 때만 push.
  강제 push·무단 merge·새 공개 저장소·운영 배포 금지.
- 중단 시 현재 변경/검사/미연결 목록/다음 시작점을 checkpoint에 남긴다.

완료 보고:
1) 코드에서 실제 확인한 회귀 원인과 고친 연결 경로.
2) profile별 전체 의류/이미지 연결/scene LED 연결/케어 적용가능/예시참고/진짜 미확정 수.
3) 현재의 생활 프로필에서 사진·LED·이력·관리 안내가 함께 나온 실제 캡처와 녹화.
4) 첨부 S01 케어 문자열의 수정 전후와, 메모가 고객 본문/AI근거에서 분리된 증거.
5) 보존한 사용자 데이터와 재적용·새로고침 검사.
6) 실제 검사 결과, commit, 원격 상태. 동봉 SOURCE_AUDIT의 입력 ZIP 검사를 앱 검사로 합산하지 않는다.

끝: 사진만 복구해 이력을 잃거나, 이력만 유지해 사진·LED가 없는 상태는 완료가 아니다.
같은 생활 프로필의 같은 의류에서 모두 함께 작동해야 한다.
