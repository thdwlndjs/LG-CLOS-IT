0. 이번 작업의 완료 모습 — 먼저 이것을 이해한다
================================================================

현재의 '옷장처럼 그린 좌우 패널 + 넓은 흰색 웹앱 + 작은 옷 이미지'를 유지한 채 꾸미지 마라.

제품 화면을 열면 첨부된 「대칭형 럭셔리 스마트 드레스룸.png」의 사진이 그대로 보여야 한다.
문, 칸, 선반, 서랍, 걸린 옷, 접힌 옷, 중앙 거울의 폭과 위치가 같아야 한다.
그 사진에서 위치 안내 LED만 기본 OFF로 바꾼다.
UI와 피팅은 사진 안의 실제 중앙 거울 유리 경계 안에서만 움직인다.
양옆 옷장에는 웹 카드, 별도 위치 격자, 옷 아이콘, 폼을 덧붙이지 않는다.

김수진:
옷장 → 옷을 옆으로 탐색 → 한 벌 선택 → 해당 보관 위치의 LED → 같은 옷의 착용 이력 → 라벨·관리법 → 옷을 가져갈 수 있는 상태.

최휘재:
홈의 오늘 추천 코디 선택 → 같은 코디가 내 전신에 적용된 코디 화면 → 다른 전체 코디 비교 → 상의만 교체 → '이 옷으로 입기' → 오늘의 선택 기록 + 구성 의류 위치 LED.

기능 버튼이 많아지는 것이 진척이 아니다.
'손으로 후보를 옆으로 살펴보고, 옷을 누르면 관련 결과가 자연스럽게 이어지는 것'이 진척이다.
모든 중간 상태를 고객에게 처리·확인 버튼으로 돌려주지 않는다.

이번 작업에서 지킬 최우선 순서:
1) 기준 사진과 동일한 장면, 정확한 미러 경계, LED OFF/ON
2) 미러의 실제 좁은 폭에 맞는 화면과 좌우 탐색
3) 두 시나리오의 대상·선택·결과·기록 연결
4) 기존 백엔드·DB·API 경로 연결 확인 및 보존
5) 오류/재진입/중복/성능/접근성 검수와 정리

================================================================

먼저 현재 폴더, Git branch/remote/status, 실행 명령, 프런트 주소·포트, 서버 주소를 확인한다.

현재 UI에서 핵심 행동의 실제 호출 경로를 추적한다:
- 옷 조회: 서버 조회인지 로컬 데모인지
- 카드 선택: 해당 카드 snapshot을 여는지, 이전 초안이 대신 열리는지

- 오늘 코디 기록: 실제 저장과 재조회가 연결되는지

키 값은 출력하지 말고 설정 유무와 경로만 확인한다.
실연동 실패를 알아보기 위해 운영 DB/사용자 데이터를 무작정 변경하지 않는다.
계정 연결/.env/서버 설정 문구가 고객용 마이에 있다면 개발 진단 영역으로 분리한다.
실제 로그인 자체를 우회하거나 인증·가족 권한을 없애서는 안 된다.

자료 경로가 다르면 현재 프로젝트와 첨부 위치 안에서 파일명·해시·이미지를 확인해 찾는다.
사용자 전체 디스크를 무제한 검색하거나 별개의 게임·프로젝트를 수정하지 않는다.
파일 하나가 없다는 이유로 전 작업을 멈추지 않는다. 그 파일 의존 부분만 명확히 보류하고 독립 작업을 진행한다.

3. 기준 사진을 그대로 쓰는 장면 구조
================================================================

3.1 원본 확인
이번에 확인된 파일은 1672 × 941 픽셀이다.
파일명: 대칭형 럭셔리 스마트 드레스룸.png
SHA-256: 95c47d8caa06019564b579c9cde4e68e5e94e46496f17937eb678d9ca535a617

같은 그림이라도 메타데이터 때문에 파일 해시가 다를 수 있다. 실제 픽셀·비율을 대조한다.
동봉 JSON의 rgb_pixel_sha256도 참고한다.
다른 장롱 이미지, UI가 이미 그려진 변형본, 과거 wireframe으로 대체하지 않는다.
이미지를 CSS 칸/선반/반복 텍스처로 재구성하지 않는다. 좌우를 임의로 대칭 복제하지 않는다.
사진 속 옷과 서랍을 다시 배치하거나, 상자·악세서리를 추가하지 않는다.

3.2 레이어
WardrobeStage 하나 안에 아래 레이어를 둔다.
L0: LED OFF 기준 배경 이미지
L1: 활성 위치에만 표시되는 LED core/glow/spill 레이어 — pointer-events:none
L2: 정확한 거울 유리 안의 MirrorViewport — overflow:hidden, isolation
L3: MirrorViewport 안의 거울 표면/피팅 미디어
L4: MirrorViewport 안의 메뉴·콘텐츠·비교 트레이·일시적 안내

개발 보조 UI는 별도 /dev 또는 로컬 개발 모드에만 둔다.
고객 UI의 포털(툴팁/선택기/다이얼로그)도 MirrorViewport에 붙인다.
body에 포털을 붙여 미러 밖으로 폼과 메뉴가 새어나오게 하지 않는다.

3.3 비율 유지
기준 사진 전체를 contain 방식으로 뷰포트 안에 맞춘다. cover로 자르거나 가로세로를 다르게 늘리지 않는다.
사진이 놓인 Stage의 실제 콘텐츠 사각형을 UI와 LED가 공통으로 사용한다.
사진 바깥 여백은 배경 여백이다. 좌표를 브라우저 전체 %로 계산하지 않는다.

기준 이미지가 (W,H), 사용 가능 화면이 (Vw,Vh)이면:
s = min(Vw/W, Vh/H)
renderW = W*s; renderH = H*s
left = (Vw-renderW)/2; top = (Vh-renderH)/2
이미지 좌표(x,y)의 화면 위치 = (left+x*s, top+y*s)

실제 CSS에서는 Stage를 renderW/renderH로 만들고 그 내부 정규화 좌표로 배치해도 된다.
중요한 것은 사진·미러·LED가 동일한 좌표계를 쓴다는 점이다.
ResizeObserver/동등한 기존 처리로 뷰포트·전체화면 변경을 반영한다.
DPR, CSS 픽셀, 원본 픽셀을 섞지 않는다.

3.4 미러의 안전 경계
원본에서 확인한 UI 안전 사각형 시작값:
x=714, y=28, width=248, height=824
정규화: x=0.4270335, y=0.0297556, w=0.1483254, h=0.8756642
금속 프레임을 침범하지 않도록 실제 배경에 겹쳐 최종 정렬한다.
이 좌표는 사진 안의 화면 위치이지 실물 mm 규격이 아니다.

1920×1080에서 이 미러의 표시 폭은 약 285 CSS px다.
이 좁은 폭을 인정한다. 기존의 400~700px 웹앱을 축소해 모든 내용을 욱여넣지 않는다.
미러 폭을 임의로 넓혀 사진과 다르게 만드는 것도 금지한다.

기준 검수는 독립 브라우저/전체화면의 1920×1080, 추가 2560×1440에서 한다.
작은 Codex 미리보기 패널에 우겨넣은 화면을 최종 가독성 근거로 사용하지 않는다.
작은 화면에서는 같은 비율을 유지한다. 부족한 공간을 해결하려고 본래 미러 밖에 패널을 추가하지 않는다.
브라우저 확대를 전역 차단하지 않는다. 별도 확대/보조 접근에서도 필수 콘텐츠를 없애지 않는다.

4. LED OFF 자산과 위치 매핑 — 특히 정확하게 처리한다
================================================================

4.1 원본의 LED는 이미 켜져 있다
CSS의 glow 레이어를 숨기는 것만으로 사진에 박혀 있는 불빛이 꺼지지 않는다.
원본은 수정하지 않고, 원본과 동일한 치수의 wardrobe-base-led-off.png 파생 파일을 만든다.
작은 점광원 중심뿐 아니라 그 주변 발광 halo도 제거해야 한다.

허용되는 편집:
- 각 위치 표시등과 그 발광 주변만 국소 마스킹/인페인팅/복원
- 동일 소재의 인접 픽셀을 이용한 자연스러운 표면 복구
- 실제 편집 마스크 파일 보존

금지되는 편집:
- 전체 장면 새 생성, 선반/문/옷/거울 배치 변경
- 검은 점/검은 사각형 덮기
- 전체 사진 brightness를 낮춰 OFF라고 부르기
- 거울에 반사된 천장 조명까지 위치 LED로 오인해 제거하기

불이 꺼진 상태에서도 사진의 일반적인 실내 조명과 옷의 가시성은 유지한다.
국소 수정 도구가 없거나 결과가 눈에 띄면 그 자산 작업만 미완료로 남긴다.
자산 실패를 핑계로 원본을 다른 사진으로 교체하지 않는다. 나머지 UI·상태·LED 좌표 구현은 계속 진행한다.

검수:
원본과 OFF 파생본을 같은 크기로 비교한다.
허용된 조명 편집 마스크 바깥 RGB는 변하지 않아야 한다(같은 색공간, lossless 기준).
마스크 안에서도 목재/옷 경계가 망가지지 않았는지 확대해 본다.
'모든 LED OFF' 화면과 '한 위치 ON' 화면을 각각 캡처한다.

4.2 좌표는 시각 표식이고, 의류와의 연결은 따로 한다
동봉 mirror_geometry.reference.json에는 원본에서 확인한 점광원 후보 34개가 있다.
이는 하드웨어 개수·수납량·정확한 의류 개수를 확정한 수치가 아니다. 34개를 모두 의류에 억지로 연결하지 말고 대표 경로에 필요한 확인된 매핑부터 완성한다.
특히 행거 옷 수와 점광원 수가 같다고 가정하지 않는다.

garmentId → 기존 location 값/출처 → visualZoneId → ledAnchorIds
이 연결을 한 곳에서 관리한다. 임의 배열 순번/옷 색/이름 일부/해시 나머지로 LED를 고르지 않는다.

필수 매핑 데이터:
- sceneAssetVersion 또는 sourcePixelHash
- 실제 garmentId (기존 ID 보존)
- visualZoneId
- ledAnchorIds[]
- 위치 출처: 실제 기록/사용자 입력/시연 fixture/unknown
- 위치 정밀도: 구역 또는 검증된 개별 위치

사진 속 보이는 의류와 기존 DB 의류가 실제로 같은 개체라는 증거는 없다.
시연 대표 옷은 외형·보관 유형이 일치하는 구역과 명시적으로 매핑하고 '시연 위치'로 둔다.
운영 데이터의 위치를 조용히 바꿔 배경과 맞추지 않는다.
한 선반에 여러 접힌 옷이 있으면 선반 단위 안내로 설명한다. 아래쪽 숨은 옷을 정확히 특정했다고 표시하지 않는다.
같은 구역의 여러 의류는 LED를 하나로 합쳐 표시하되 미러에서 해당 구성품 이름을 확인할 수 있게 한다.
위치 unknown에는 임의 점등을 하지 않는다.

4.3 상태에 따른 점등
기본/홈: 모두 OFF.
옷 목록을 drag/hover/focus로 살펴보기만 함: 기존 점등을 바꾸지 않음.
김수진이 의류를 tap: 선택 의류의 위치만 ON.
그 의류의 착용이력 ↔ 라벨·관리법 이동: 같은 위치 ON 유지.
다른 의류를 tap: 이전 위치 OFF, 새 위치 ON.
옷 목록으로 돌아와 선택 해제, 홈 복귀, 사용자 변경: OFF.

최휘재 코디·상의 비교 중: 최종 회수용 LED는 OFF.
'이 옷으로 입기' 확정: 최종 snapshot의 보유 의류 위치들을 ON.
현재 코디를 확인하는 캘린더 왕복: 해당 회수 대상은 유지 가능.
새 비교 시작/다른 코디 확정/사용자 변경/홈 복귀: 이전 회수 표시 해제 또는 새 집합으로 교체.
알 수 없는 위치가 한 개 있다고 다른 정상 위치까지 꺼버리지 않는다.

4.4 모양
기본 점등색은 원본과 어울리는 따뜻한 백색/앰버로 통일한다.
이미지 원본 기준 core 반경 약 2~3px, glow 반경 약 10~18px부터 조정한다.
구역 내부에만 매우 약한 spill을 추가할 수 있으나 가구 전체를 노랗게 덮지 않는다.
150~220ms 점등, 180~260ms 소등을 시작값으로 사용한다.
지속 깜박임·무지개·동시에 모든 위치 점등·커다란 노란 마커는 사용하지 않는다.
LED 레이어가 클릭을 가로채거나 미러 UI를 덮지 않게 한다.

================================================================
5. 미러 UI의 구체적인 공간 규칙
================================================================

5.1 공통 구성
미러 내부의 상대 좌표를 u(가로 0~1), v(세로 0~1)로 정의한다.
- 표면 여유: 가장자리 약 3~4% (프레임/빛 번짐과 콘텐츠 겹침 방지)
- 얇은 상황 헤더: v=0.06~0.12, 제목/현재 사용자/짧은 실행 출처
- 왼쪽 메뉴 레일: u=0.015~0.17, v=0.27~0.65
- 본문: u=0.19~0.96
- 손이 주로 닿는 비교·조작 영역: v=0.28~0.64
- 하단 여백 v=0.79 이후: 기본적으로 반사/피팅의 하체·발 영역. 버튼을 쌓지 않음

주요 CTA의 중심은 v=0.57~0.62를 시작값으로 배치한다.
정보를 위쪽 25%에만 몰거나 CTA를 발밑에 넣지 않는다.
비교·케어 설명은 가로 장면으로 나눠 이 범위 안에서 읽힌다. 긴 세로 문서가 되면 잘못 구현한 것이다.

좌표는 실제 콘텐츠·글꼴 검수 뒤 몇 % 조정할 수 있다.
미러 경계를 넓히거나 글자를 계속 줄여 해결하지 않는다. 먼저 동시 표시량을 줄인다.

5.2 여섯 메뉴
홈/옷장/코디/캘린더/케어/마이만 유지한다.
작은 일관된 선 아이콘 + 짧은 한국어 이름을 쓴다. 2×3 대형 버튼판으로 만들지 않는다.
현재 메뉴만 잔잔한 색 배경으로 강조한다.
화면 모드에 따라 옷장/케어/코디의 활성 메뉴를 올바르게 표시한다.
레일은 이미지를 덮는 좁은 UI일 뿐, 별도 불투명 사이드바가 아니다.

1920×1080 기준 메뉴 아이콘은 18~20 CSS px, 터치영역은 약 44×44 CSS px부터 사용한다.
글자: 본문/의류명 16~18px, 보조 13~14px, 제목 20~24px, 시간 34~40px 시작값.
작은 메뉴 라벨을 제외하고 중요한 내용을 12px 미만으로 줄이지 않는다.
시연용 실제 물리 터치판의 mm 도달성은 별도 실기 검증 대상임을 구분한다.

5.3 반사·투명도
일반 홈/옷장/케어에서는 원본의 밝은 거울 반사를 볼 수 있어야 한다.
전체 미러를 불투명 흰색 또는 검은색 앱 화면으로 채우지 않는다.
글자가 필요한 곳에만 얇은 frosted panel을 사용한다.
시작 테마: 뉴트럴 스톤/샌드, 차분한 세이지 강조, 텍스트 차콜 또는 흰색(패널에 맞춤).
예: 작은 정보 패널 배경 rgba(245,244,238,0.78~0.88), 경계 얇게, radius 12~16px.
거울 위 직접 흰 글자는 국소적으로 대비를 확보하고 약한 그림자로 보조한다.
거울 전체를 가볍게 보정해야 하면 opacity 0.08~0.16 범위의 국소 scrim부터 확인한다.
정해진 alpha를 지키려고 읽기 어려운 화면을 방치하지 않는다. 실제 배경 위에서 대비를 검사한다.

부모 컨테이너 전체에 opacity를 줘 글자·의류·영상까지 흐려지게 하지 않는다.
피팅 옷의 색을 바꾸는 전체 multiply/filter를 쓰지 않는다.
중첩 유리 패널 3겹, 과한 blur, 그림자, 테두리, 모든 카드의 버튼화는 피한다.

5.4 화면당 행동 수
주 행동은 최대 1개를 기본으로 한다. 필요한 보조 행동은 1개 정도다.
메뉴·탭·이전/다음 접근성 컨트롤은 독립 역할로 유지할 수 있지만, 동일 행동 버튼을 중복 배치하지 않는다.
'분석하기→적용하기→반영하기→확인하기→저장 확인하기'를 한 작업의 필수 단계로 만들지 않는다.
저장 확인서/작업 번호/상태 enum은 내부 기록이며 고객용 버튼이 아니다.
출처표시·중요한 불확실성은 숨기지 말고 한 곳에 짧게 표시한다. 디버그 문장으로 화면을 도배하지 않는다.

================================================================
6. 가로 탐색: 브라우저 스크롤을 숨기는 게 아니라 직접 조작으로 만든다
================================================================

6.1 구현 방식
기존 컴포넌트로 가능하면 재사용한다. 불필요한 새 UI 프레임워크를 설치하지 않는다.
직접 구현 시 Pointer Events 기반 단일 HorizontalPager/Carousel을 재사용한다.
옷 목록/홈 코디/코디 후보/상의 후보/상세 내부 페이지에 같은 조작감을 적용한다.
모든 메뉴를 스와이프로 순환시키는 전역 carousel은 만들지 않는다.
원본 영상·인물은 후보 트랙에 포함하지 않는다. 후보만 움직이고 인물 위치는 유지한다.

6.2 기본 동작 값 (CSS px 기준, 조정 가능한 토큰)
- pointerdown: 좌표만 기록. 선택/실행하지 않음.
- 누적 이동 8px 전: 탭 후보.
- |dx|>8px 및 |dx|>1.2*|dy|: 가로 드래그 확정.
- 드래그 중: 손 이동에 1:1로 반응. 프레임마다 transition으로 지연시키지 않음.
- 손을 놓았을 때: 이동이 카드 폭의 약 22% 이상 또는 |vx|>0.5px/ms이고 이동 12px 이상이면 다음/이전 한 장.
- 그보다 작은 이동: 원래 위치로 복귀.
- 정착: 240~320ms, 시작값 cubic-bezier(0.22,0.61,0.36,1).
- 양 끝: 제한된 저항(예: 이동의 18%) 후 제자리. 무한 순환하지 않음.
- 작은 폭에서는 큰 카드 1장 + 옆 카드 10~15%가 보이게 한다. 3열 그리드를 억지로 넣지 않음.

드래그한 뒤 발생하는 click은 억제한다. 다음 실제 탭까지 영구 차단하지 않는다.
pointercancel/lostpointercapture/화면 전환/resize 때 드래그를 안전하게 끝낸다.
세로 드래그는 주요 제품 페이지를 밀어내지 않으며, 탭으로 오인되지 않는다.

손가락·마우스 드래그 둘 다 지원한다. 일반 Pointer capture와 touch-action을 정확히 사용한다.
가로 영역에는 pan-y pinch-zoom 같은 적절한 touch-action을 사용해 가로 제스처 처리를 소유하되,
전역적으로 pinch 확대를 막거나 모든 pointer 이벤트에 preventDefault하지 않는다.
폼·라벨 확대·버튼의 클릭을 부모 carousel이 가로채지 않게 한다.

6.3 대체 조작
작은 이전/다음 chevron에 충분한 터치영역을 두고, 키보드 방향키는 탐색만 수행한다.
Enter/Space는 실제 선택이다. Tab 포커스가 숨은 카드에 갇히지 않게 한다.
reduced-motion에서는 이동량/애니메이션을 줄여도 동일한 일을 끝낼 수 있게 한다.
스크롤바만 안 보이게 한 긴 세로 페이지는 금지한다.

6.4 선택과 적용
browsedIndex: 옆으로 살펴보는 위치.
selectedGarmentId/selectedLook: 사용자가 tap한 대상.
displayedLook: 실제로 정상 표시가 확인된 피팅 결과.
이 셋을 하나의 state로 합치지 않는다.
드래그/hover/자동 포커스 이동만으로 새 추천, 피팅, 저장, LED 점등을 시작하지 않는다.

================================================================
7. 화면별 명세 A — 김수진: 옷 찾기에서 케어까지
================================================================

공통: 수진에게 허용된 가족 의류만 사용한다. 화면을 보여주려고 타인 권한을 우회하지 않는다.
현재 프로필은 기존 방식으로 사전 선택한다. 고객 화면에 페르소나 시연 메뉴를 새 제품 기능처럼 넣지 않는다.

A1. 옷장 탐색
진입: 왼쪽 '옷장'.
헤더: '내 옷장', 현재 가족 범위 작은 표시.
검색/가족 필터는 기존 기능을 유지하되 기본 화면을 여러 입력폼으로 채우지 않는다.
가족 선택이 필요하면 얇은 선택기 하나. 검색은 아이콘으로 열며 취소/닫기 때 조건 보존.

본문 배치 예:
v=.22~.27 간단한 범위/종류 필터
v=.29~.53 큰 의류 카드 하나 + 다음 카드 일부
v=.53~.60 의류명/소유자, 짧은 보관 위치
카드 전체가 '상세 열기'다. 같은 카드에 상세/위치/케어/이력 버튼 4개를 붙이지 않는다.

가로로 넘기기만 해서는 선택·LED·이력을 변경하지 않는다.
대표 옷 tap 시 selectedGarmentId를 고정하고 즉시 해당 위치를 점등한다.
같은 옷의 상세로 180~240ms 부드럽게 이어진다. 가능하면 사진이 같은 자리에서 이어지는 짧은 전환.
큰 위치 격자나 별도 측면 패널을 띄우지 않는다.

A2. 같은 옷의 착용 이력
공통 헤더: 작은 뒤로 + 같은 옷 이름/소유자.
작은 의류 사진/마지막 위치(v=.18~.34)는 계속 유지한다.
상세 내 두 면: '착용 이력' / '라벨·관리법'. 얇은 탭과 수평 페이지 이동을 함께 제공한다.
첫 면은 착용 이력.

보여줄 데이터:
- 마지막 착용일 (실착 근거가 있는 이벤트)
- 마지막 세탁 이후 착용 기록 횟수, 계산 가능한 경우
- 마지막 확인된 세탁일
필요하면 최근 날짜 몇 개를 보여준다. 몇 일 경과를 실제 며칠 착용으로 표시하지 않는다.
오늘 선택만 한 코디, 피팅 결과, 저장 카드 수는 착용 횟수에 넣지 않는다.
정보가 없으면 해당 항목만 '기록 없음'. 화면 전체를 거절/오류로 만들지 않는다.
'세탁 필요 확정' 자동 배지나 근거 없는 권장 주기를 만들지 않는다.

사용자는 이 기록을 보고 세탁 필요를 판단한다. '세탁이 필요하다고 판단 완료' 버튼은 필요 없다.

A3. 라벨·관리법
같은 옷을 유지한 채 탭 또는 옆 넘김으로 진입한다. 케어 활성 메뉴를 정확히 표시한다.
상단의 옷/위치 문맥은 유지하고 body만 바뀐다.
라벨 원본 축소 미리보기 → 근거에 맞춘 세탁/건조/주의 요약 최대 3항목.
원본이 작으면 tap으로 같은 미러 내부의 읽기 전용 확대 페이지를 열고, 닫으면 원 위치로 돌아온다.
핵심 라벨 금지사항을 짧게 쓰겠다고 생략하지 않는다. 필요하면 요약/원문 가로 2면을 쓴다.

이미 있는 라벨·가이드는 조회한다. 화면 진입마다 에이전트를 다시 실행하지 않는다.
실제 준비된 근거가 있고 새 설명이 필요한 기능은 기존 승인된 requestCareGuide 경로로 연결한다.
자동으로 새 유료 작업을 반복하지 않는다.

라벨 없는 예외는 실제로 있는 자료/기록을 보여주고 '라벨을 아직 확인하지 못했어요'를 한 번 알린다.
대표 시나리오는 라벨과 정상 안내가 있는 옷으로 완성한다. 모든 옷을 '근거 없음'으로 끝내고 완료라 하지 않는다.

A4. 옷을 가져갈 수 있는 상태에서 끝
위치 LED는 같은 의류에 유지한다.
미러 하단 작업 영역에는 필요 시 '불이 켜진 위치에서 꺼내세요' 같은 한 줄 안내만 둔다.
'옷 회수 완료', '세탁 완료', '다음', '기록 확인' 버튼을 의무적으로 추가하지 않는다.
선택/이력/라벨 조회 전체에서 garments/착용/관리/이동 기록을 새로 쓰지 않는다(기존 감사 로그는 별개).
실물 회수는 사람의 발표 행동이다. 사진 속 옷이 자동으로 사라지거나 이동하는 애니메이션을 만들지 않는다.

뒤로 동작:
라벨 원문 확대 → 케어 요약 → 선택 옷 상세 → 원래 검색·가족 범위·목록 index 복원.
다른 옷 케어에 들어가면 이전 옷의 완료/오류/안내가 대신 뜨지 않아야 한다.

================================================================
8. 화면별 명세 B — 최휘재: 추천 카드에서 상의 교체·기록까지
================================================================

B1. 홈
현재 사용자에게 연결된 시간/날짜를 한 곳에서 읽는다. 화면마다 서로 다른 날짜를 만들지 않는다.
실시간 시계와 고정 시연 날짜는 별도 모드다. 고정 시연 자료를 실제 오늘 데이터인 것처럼 표시하지 않는다.
날씨는 이미 있는 확인된 값만 짧게 사용하며 이번 UI 작업 때문에 새 위치 권한/API를 추가하지 않는다.

배치 예:
v=.15~.24 시간/날짜
v=.28~.32 '오늘의 코디'
v=.33~.55 추천 카드 1장 + 다음 카드 일부
v=.55~.61 현재 카드 이름·한 줄 맥락·'눌러서 미러로 보기' 안내
케어 알림이 필요한 홈이라면 아래 작은 행 1개. 긴 알림 목록/캘린더/최근작업 로그를 홈에 펼치지 않는다.

카드 전체가 행동 대상이다. '상세', '선택', '적용', '피팅 시작'을 카드 안에 나열하지 않는다.
단순 옆 탐색은 호출 0회.
카드를 tap하면 그 카드의 outfitId/snapshot/자산버전이 코디 화면으로 전달된다.
다른 이전 편집 초안이 선택 카드 대신 조용히 열리면 실패다.
이전 초안과 원본 카드는 보존하고, 현재 비교는 새 작업 문맥에서 시작한다.

이 tap은 '해당 코디를 미러로 비교하기' 의도가 명확한 진입 행동이다.
승인된 live 경로가 준비된 경우 여기서 한 번 startTryOn으로 연결할 수 있다.
React render/중복 mount/자동 캐러셀 때문에 연결이 여러 개 생겨서는 안 된다.
메뉴만 눌러 단순 코디 목록으로 들어오는 것과 이 명시적 카드 선택을 구분한다.

B2. 미러 속 전체 코디 비교
주 화면은 전신 미디어다. 작은 popup/준비결과 확인창을 주 화면으로 쓰지 않는다.
같은 승인된 인물 입력, 같은 시점/크기/정렬 조건을 최대한 유지한다.
전신은 u=.04~.97, v=.09~.94 안에서 비율을 보존해 배치하는 것을 시작값으로 한다.
머리/손/발/신발을 자르거나 몸을 좁게 찌그러뜨려 미러를 채우지 않는다.

중요한 폭 제약:
이 미러는 약 1:3.3의 좁고 긴 영역이다. 9:16 영상 전체를 단순 cover하면 인물이 잘릴 수 있다.
이미 준비된 인물 자산에서 인물 밖의 불필요한 여백만 안전하게 줄일 수 있는지 확인한다.
인물 전체가 움직일 때도 안 잘리는 crop/safe region을 자산별로 확인한다.
전처리가 없다면 contain으로 전체를 보존한다. 작은 전신이 되는 한계는 기록하고 준비 자산 개선 대상으로 남긴다.
확인하지 않은 배경 제거/실루엣 잘라내기를 임의 도입해 붙여놓은 모델처럼 만들지 않는다.
원본 미러 반사와 영상 배경의 경계가 튀지 않도록 주변 여백에만 부드러운 mask를 쓸 수 있다.
인물·의류에는 색/명암 필터나 투명화를 적용하지 않는다.

UI는 '후보를 조작할 때'와 '전신을 볼 때' 표시 밀도를 다르게 한다.
항상 큰 선택 패널을 인물 위에 고정하는 것은 금지한다.

[후보 트레이 펼침]
- v=.40~.55 부근의 단일 얕은 유리 트레이 안에서 코디 썸네일을 옆으로 탐색한다.
- 작은 썸네일은 2개 정도만 보이게 하고, 전체 코디를 보는 주 화면과 혼동하지 않는다.
- v=.56~.62에는 1차 CTA '이 옷으로 입기'.
- '상의 바꾸기'는 같은 문맥의 보조 액션 1개(얇은 텍스트/칩).
- 트레이가 전신을 일부 가리는 것은 조작 중에만 허용한다.

[전신 관찰 상태]
- 후보 적용 결과가 실제 표시된 뒤, 손이 떨어져 있고 0.8~1.2초 새 조작이 없으면 큰 트레이를 작은 비교 바(약 44~52 CSS px 높이)로 접는다.
- 축소 바에는 현재 비교 대상/후보 다시 열기와 주요 선택 행동만 남긴다. 저장 목록이나 조건 폼은 없다.
- 얼굴·상의 앞면·바지 형태를 지속적으로 가리지 않게 한다.
- 현재 의류와 겹치면 같은 높이의 여백 쪽으로 compact 바를 조정하거나, 미러 빈 공간을 tap해 조작부를 일시 숨길 수 있게 한다.
- 완전히 숨긴 상태에서도 왼쪽 레일의 현재 '코디' 또는 조용한 '비교' 핸들을 tap하면 원 트레이를 복원한다. 복원은 API를 호출하지 않는다.
- 이 관찰 상태는 매 후보마다 반드시 눌러야 하는 별도 단계가 아니다. 직접 후보 비교 흐름을 끊지 않는다.
- pointerdown/drag/입력 편집/키보드 focus-visible 중에는 자동 접힘을 멈춘다. 마우스 tap 뒤 버튼에 남은 포커스만으로 영구적으로 펼침 상태에 고정하지 않는다. 버튼을 누르려는 중 위치가 바뀌면 실패다.
- 접근성 포커스와 키보드 사용 중에는 갑자기 컨트롤을 없애지 않는다.

카드 tap: selectedLook 갱신 → applyTryOnLook.
단순 카드 swipe: browsedIndex만 변경.
전신 인물 자체가 카드와 함께 옆으로 슬라이드하지 않는다.

B3. 상의만 교체
'상의 바꾸기'를 누르면 후보 트레이의 데이터가 보유 상의로 바뀐다.
하의·그 외 원 조합에 있던 품목은 그대로 유지한다. 원래 없던 가방/아우터를 새 필수 품목으로 만들지 않는다.
화면에는 '상의만 바꾸기'와 현재 상의 이름이 보인다.
'고정'은 유지 중인 나머지 품목을 알려주는 상태다. 불필요한 잠금 해제 버튼을 새로 만들지 않는다.

상의 후보 tap:
현재 전체 look에서 top slot만 교체 → revision 증가 → 같은 세션에서 전체 look state 적용.
다른 슬롯이 바뀌면 실패.
추가 '교체 적용' 버튼은 없다. 최신 시나리오에서는 tap이 이미 시작된 피팅 비교에 반영되는 행동이다.
단, 기존 세션/승인이 없는데 목록 hover만으로 새 유료 세션을 열지는 않는다.

같은 후보 재선택은 선택 해제·새 요청을 만들지 않는다.
빠른 연속 tap은 마지막 선택을 화면에서 바로 표시하되, 공급자 갱신은 직렬화한다.
이미 전송된 작업은 처리/기록을 유지하고 아직 전송되지 않은 중간 후보는 최신 하나로 합친다.
무제한 병렬 생성/자동 재연결/매번 새 OpenAI 호출은 금지한다.
전체 코디 보기로 돌아오면 원본 카드와 편집 중인 새 조합을 구분한다. 원본 카드를 덮어쓰지 않는다.

B4. 결과 대기·전환
selectedLook과 displayedLook을 별도로 유지한다.
선택한 이름은 최신 후보를 표시하되, 영상이 이전 결과이면 반드시 '이전 결과 · 새 코디로 바꾸는 중'과 같이 구분한다.
1초짜리 타이머가 지났다는 이유만으로 displayedLook을 새 조합으로 확정하지 않는다.
실제 공급자 상태/결과 metadata/표시 확인을 이용한다. 연결 성공만으로 의류 일치까지 검증됐다고 쓰지 않는다.

상태:
미연결 / 연결 중 / 변환 표시 / 조합 전환 중 / 실패 / 종료.
실패해도 선택 조합과 원본 의류는 보존한다.
실제 결과가 없는데 카드 사진을 생성 영상처럼 움직여 성공으로 만들지 않는다.
저장된 결과가 있으면 사용자에게 출처를 알리고 재생 경로를 제공할 수 있다. 몰래 live를 대체하지 않는다.
실제·준비입력·저장재생 구분은 미러의 작고 읽을 수 있는 상태 표시 1곳에 유지한다.

B5. '이 옷으로 입기'
한 번 누르면 현재 사용자, 현재 날짜, 최종 의류 ID/슬롯/자산버전, look revision을 불변 snapshot으로 고정한다.
캘린더에 '오늘 선택한 코디'를 기록하고, 같은 최종 snapshot의 위치들을 점등한다.
별도 '코디 저장 → 적용 → 기록 확인 → 위치 찾기' 4단계를 만들지 않는다.

기록 의미:
실제 입기 전 선택이므로 계획/선택 이벤트(planOutfit 또는 현재 코드의 동등한 작업)다.
실제 착용 이벤트(recordWear), 착용 횟수, 세탁/청결/반납 상태를 자동 변경하지 않는다.
사용자에게 보이는 제목은 '오늘의 코디', 짧은 상태는 '선택한 코디'로 한다.
이번 시나리오 때문에 새로운 Actual Wear 촬영/확인 과정을 필수 삽입하지 않는다.

저장/LED 처리:
- 저장 결과 대기와 무관하게 선택한 옷의 위치 안내 자체는 할 수 있다. LED는 저장 성공의 증거가 아니다.
- 한 작업에서 시작하되, '기록했어요'는 실제 저장 확인 뒤에만 표시한다.
- 저장 실패/결과 불명에도 현재 조합과 위치 안내는 유지한다. 실패 안내를 작게 표시하고 원 요청 조회/재시도 경로를 사용한다.
- 같은 의도/같은 revision의 더블클릭과 재전송으로 기록을 여러 개 만들지 않는다.
- 저장 중 새 편집이 필요하면 원 snapshot은 유지하고 새 초안으로 분리한다. 늦은 성공이 현재 조합을 바꾸면 안 된다.

피팅이 미완료라는 이유만으로 모든 코디 저장을 일률 차단하지 않는다.
단, 미리보기가 이전 조합이면 지금 어떤 조합을 기록하는지 썸네일/의류명으로 분명히 해야 한다.
잘못된 old displayedLook을 저장하거나 새 조합을 이미 보았다고 표시하면 실패다.

기존 서버 작업이 outfit snapshot 저장과 계획 이벤트 저장을 요구하면 기존 계약으로 연결한다.
새 백엔드 체계를 만들지 않는다. 중간 성공/응답 유실을 감출 수 없는 구조라면 결과 확인 상태를 정확히 유지한다.
단순 UI 수정을 위해 기록 원자성/중복 방지를 제거하지 않는다.

B6. 마무리와 재조회
미러에는 최종 전신/조합을 유지하고 '오늘의 코디를 기록했어요' 한 줄 안내를 2~3초 표시한다.
자동으로 캘린더 전체 화면으로 밀어내지 않는다.
원하는 경우 기존 캘린더 메뉴에서 오늘의 선택 카드와 동일 구성품을 다시 확인할 수 있어야 한다.
위치 LED는 선택한 옷을 꺼내는 동안 유지한다. 선택을 바꾸거나 홈/사용자를 바꾸면 규칙에 맞춰 해제한다.
회수 확인을 위해 배경 속 옷을 클릭하거나 사진에서 옷을 없애게 만들지 않는다.

최종 확정 후 계속 생성할 이유가 없으면 기존 정책으로 피팅을 종료한다.
실제 출력의 마지막 프레임을 보존할 수 있으면 '선택 결과'로 유지한다(실시간인 척하지 않음).
영상 캡처가 권한·브라우저 조건상 안 되면 승인된 저장 결과/최종 구성품을 유지하고 생성 루프를 무기한 켜두지 않는다.
모든 owned stream track/listener/재연결 타이머를 정리한다.

================================================================
9. 기능 연결의 최소 상태 구조 — UI와 사실을 섞지 않는다
================================================================

기존 store/router/서버 contract를 먼저 사용한다. 아래는 의미 모델이지 강제 파일명/새 프레임워크가 아니다.

공통:
actorContext, navSection, returnContext, sceneVersion

옷장:
query/filter, browsedIndex, selectedGarmentId, detailPanel(history/care/labelOriginal)

코디:
sourceOutfitId, workingLook, lookRevision, mode(outfit/topSwap), browsedCandidateIndex,
selectedLook, displayedLook, fittingSessionGeneration, pendingProviderApply

위치:
illuminationIntent(kind=none|garmentFocus|confirmedLook, targetIds, locationSources)

확정:
commitIntentKey, submittedSnapshot, commitState, receiptRef

별도:
읽기 로딩/오류, AI 작업 상태, 일시 안내 상태, 원래 의류/코디/이벤트 데이터.

효과 분리:
- navigation과 list browse는 DB 쓰기/새 유료 API 0회.
- wardrobe selection은 조회/시각 LED만 변경.
- care read는 실제 care event 0개.
- fitting apply는 선택 버전과 공급자 버전을 비교.
- commit은 별도 명시 사용자 의도로 한 번만.

오래된 케어 완료화면, 다른 옷의 라벨, 이전 카드의 코디, 다른 가족의 입력이 재사용되지 않게 한다.
화면별 local state를 통째로 공유해 'success=true'가 다음 화면으로 퍼지지 않게 한다.
계획/선택 기록은 실제 착용 횟수 계산에서 제외한다.

================================================================
10. 대표 자산을 먼저 제대로 연결한다
================================================================

보유 자산과 실제 저장소를 읽고 대표 의류를 고른다. 이름만 맞춰 새 ID를 계속 만들지 않는다.

A 대표 1벌 필수:
사진, 허용 소유자, 위치 매핑, 실제 또는 명시된 시연 착용기록, 실제 라벨/안내 근거.
B 대표 조합 최소 구성:
홈에서 비교할 서로 다른 기존 코디 2개 이상,
그중 하나에서 교체할 상의 후보 3개를 우선 목표로 확보,
유지할 하의와 원 조합의 다른 품목,
같은 인물 입력, 전체 조합 참조/실제 결과 또는 출처가 명확한 재생 자산,
최종 구성품의 위치 매핑.
이 수량은 이번 반복 비교를 검수하기 위한 준비 목표이지 전체 제품 제한이 아니다.

원본 이미지 파일·의류 ID·미러 thumbnail·추천 카드·피팅 입력·오늘 기록을 같은 manifest로 연결한다.
핵심 비교 대상에 '사진 준비 중'만 남기고 완료 처리하지 않는다.
대표 경로에 맞는 기존 자산을 우선 사용하고, 부족하면 해당 미디어 작업을 구체적으로 남긴다.
권한 확인 없이 사용자의 인물 사진을 외부로 전송하거나 새 인물 영상을 생성하지 않는다.
라벨 원문이 없으면 소재·세탁 지침을 창작하지 않는다.
정적 배경에 있는 셔츠와 디지털 의류가 정확히 같은 상품이라고 주장하지 않는다. 시연 매핑임을 보존한다.

다른 사용자의 자산을 재사용하거나 전체 가족 자료를 한꺼번에 공급자에게 보내지 않는다.
새 데모 데이터를 써야 하면 기존 운영 자료와 분리된 허용된 시연 범위에만 추가한다.
fixture가 실제 서버 데이터인지 시험 대체 데이터인지 실행 기록에서 분명히 구분한다.

================================================================
11. 기존 연결을 보존하면서 자동 작업을 진행할 권한 범위
================================================================

중간에 사용자가 응답하지 않아도 진행할 것:
- 범위 내 프런트 코드 수정과 필요 최소한의 비파괴 연결 수정
- 배경 국소 파생자산/좌표/실제 UI 구성
- 기존 자료 기반 시연 fixture 및 테스트용 결과 매핑
- 로컬 서버 실행, 타입검사/빌드/테스트, 브라우저 캡처와 녹화
- 실패 재현·수정·회귀 검사
- 관련 파일의 단계별 로컬 commit

조건부 진행:
- 실제 API 시험은 이미 승인된 공급자/인물·의류 자산/모드/총 비용·시간 상한이 명확히 확인되는 경우에만 그 잔여 범위 내에서 소규모로 한다. 남은 실행 한도를 강제할 수 없으면 유료 시험은 보류한다.
- 키가 있다는 사실, 남은 크레딧이 많다는 말, 사용자가 잔다는 사실은 무제한 유료 실행 허가가 아니다.
- 테스트는 기본적으로 provider mock으로 지연·오류를 재현한다. 매번 유료 생성하지 않는다.
- 팀 remote/branch와 권한이 확인되고 운영 자동배포를 일으키지 않는 경우에만 push한다.

하지 말 것:
새 결제/크레딧 충전, 공급자·모델 임의 변경, 장기 키 공개,
운영 DB reset/드롭/대량 수정, 파괴적 migration, 인증/RLS 해제,
타인의 작업 rollback, force push, 자동 merge, 저장소 공개 전환, 운영 배포,
사용자 부재를 이용한 권한 승인 우회.

승인·자산·접근 문제는 해당 작업만 BLOCKED로 기록한다.
전부 중단하거나 아무 메시지 없이 대체물을 성공으로 표시하지 않는다.
같은 실패를 동일한 조건으로 무한 반복하지 않는다. 원인별 유한 횟수 재시도 후 대안/독립 작업으로 이동한다.

================================================================
12. 작업 순서 — 사람 승인 대신 자체 검수로 연속 진행한다
================================================================

P0 / 시작점 보존·연결 조사
기준 이미지, 현재 화면, 실행 경로, 변경 전 Git 상태를 확인한다.
현재의 잘못된 UI 캡처와 정상 호출 경로를 짧게 기록한다.

P1 / 외형과 미러 셸
원본 동일 장면 → LED OFF 파생 → 정확한 MirrorViewport → 고정 메뉴 → 원본과 겹침 검수.
잘못된 선반/가짜 옷장 패널/미러 밖 UI를 먼저 제거한다.
상호작용보다 먼저 배경·경계가 맞는지 스스로 캡처를 열어 확인한다.

P2 / 공통 가로 조작
카드 1장+peek, 손을 따라가는 이동, 탭/드래그 분리, pointercancel/끝 처리.
현재 앱 데이터로 옷장 또는 홈 한 곳에서 검수한 뒤 재사용한다.

P3 / 김수진 경로
대표 옷 → 올바른 위치 → 같은 옷의 이력/라벨 → 돌아가기.
잘못된 쓰기 이벤트가 없는지 확인한다.

P4 / 최휘재 경로
홈 카드 전달 → 전신 비교 → 상의만 교체 → 현재 snapshot 확정 → 기록·위치 → 재조회.
기존 백엔드/피팅 실행기를 새 미러 UI에 실제로 연결한다.
승인 불명 live만 보류해도 전체 UI 연결·재생·오류 검수는 진행한다.

P5 / 자산·미디어 보강 및 교차 검수
대표 경로의 미완성 사진, 라벨, 위치매핑, 영상 비율을 우선 보강한다.
다른 기능을 추가하기보다 두 경로가 끝까지 가능한지 확인한다.

P6 / 회귀·캡처·녹화·Git
아래 검사표를 실제로 실행하고 결과를 남긴다.
치명적 문제를 수정한 뒤 두 시나리오를 다시 녹화한다.
캡처를 만들기만 하지 말고 반드시 직접 열어 보고 기준과 비교한다.
통과한 수정은 commit하고 조건이 맞는 원격에만 push한다.

각 P단계에서 '이대로 진행할까요?'라고 사용자 답을 기다리지 않는다.
이 문서 안의 되돌릴 수 있는 UI 판단은 직접 결정하고 결과·이유를 작업 로그에 남긴다.
새 제품 범위/비용/권한 결정이 필요한 부분만 분리해 다음에 묻는다.
기본 구조만 만들고 멈추거나 계획서를 여러 개 더 쓰는 것으로 시간을 소모하지 않는다.

도구가 지원하면 병렬 작업을 사용할 수 있다:
- 장면/LED 파생자산·좌표
- 공통 미러 UI/가로 탐색
- 시나리오 상태/백엔드 연결 점검
- 독립 검수
공통 state contract는 먼저 공유한다. 같은 파일/DB를 여러 작업자가 동시에 덮지 않게 한다.
지원되지 않는 병렬/MCP/장기실행 기능이 있다고 가정하지 않는다. 가능한 환경에서는 순차로 진행한다.

================================================================
13. 최소 완료 검사 — 스크린샷과 동작을 함께 검사한다
================================================================

A. 외형/좌표
A01 원본과 동일한 가구/옷/거울 배치다. 사진을 CSS로 재현한 것이 아니다.
A02 기본 OFF에서 기존 점광원 halo가 남아 '켜짐'으로 보이지 않는다.
A03 한 점/구역 ON과 OFF가 구별되고, 다른 구역은 그대로다.
A04 1920×1080, 2560×1440, 실제 실행 창 resize에서 배경/미러/LED가 함께 정렬된다.
A05 모든 고객 overlay의 bounding box가 MirrorViewport 경계 안이다. 포털 포함.
A06 큰 흰 웹앱, 외부 위치격자, 반복 옷 텍스처, floating garment sprite가 없다.

B. 상호작용
B01 주요 두 경로를 세로 페이지 스크롤 없이 완료한다. 단순 overflow:hidden으로 숨긴 콘텐츠가 없다.
B02 느린 드래그는 손을 따라간다. 손을 놓은 뒤만 정착 애니메이션이 있다.
B03 짧은 이동 복귀/빠른 이동/경계/방향 반전/pointercancel이 정상이다.
B04 드래그 종료가 의류 선택·피팅·저장으로 오인되지 않는다.
B05 이전/다음 tap과 키보드로도 과업을 수행할 수 있다.
B06 reduced-motion에서도 기능이 사라지지 않는다.
B07 캐러셀 이동으로 미러의 전신·메뉴·가구가 같이 밀리지 않는다.

C. 김수진
C01 가족 범위·사진·위치가 같은 garmentId로 연결된다.
C02 옷 tap 한 번으로 해당 위치 LED와 상세가 이어진다.
C03 상세/케어/라벨원문에서도 대상이 바뀌지 않고 원 검색으로 복귀한다.
C04 실제 착용/계획/날짜 경과/세탁 이력의 의미가 섞이지 않는다.
C05 준비된 정상 라벨 사례에서 유용한 관리법을 읽을 수 있다.
C06 이 시나리오를 마쳐도 세탁 완료·실물 이동·착용 이벤트가 새로 생기지 않는다.
C07 다른 옷으로 바꾸면 이전 완료·오류·라벨·LED가 잘못 남지 않는다.

D. 최휘재
D01 누른 홈 카드와 코디 화면의 첫 조합이 정확히 같다.
D02 스와이프만 할 때 호출 수가 늘지 않고, 카드 tap 때만 해당 조합이 적용된다.
D03 상의 교체 뒤 top만 바뀌며 하의/나머지 원 구성은 동일하다.
D04 느린 이전 피팅 결과가 새 selectedLook을 덮지 않는다.
D05 이전 영상이 보일 때 새 코디 완료라고 표시하지 않는다.
D06 head/hand/foot crop, 신체 왜곡, 비교 중 얼굴/체형 교체가 없는지 실제 영상으로 확인한다.
D07 큰 후보 트레이는 관찰 시 접히고, 재조작 시 복원되며 포커스/드래그 도중 이동하지 않는다.
D08 '이 옷으로 입기'의 저장 대상·날짜·의류와 점등 대상이 동일 snapshot이다.
D09 더블클릭/저장 응답 유실/재진입으로 같은 의도의 오늘 기록이 중복되지 않는다.
D10 오늘 기록은 선택/계획이며 실제 착용 횟수를 늘리지 않는다.
D11 저장 뒤 자동 캘린더 전환 없이 미러의 최종 조합/위치가 유지된다.
D12 캘린더를 열면 같은 오늘 선택을 다시 확인한다.
D13 피팅 종료/홈 이탈/사용자 변경 때 연결·트랙·타이머가 정리된다.

E. 연결/보존
E01 프런트의 실제 API/데이터 경로와 현재 실행 빌드가 확인된다.
E02 기존 live 경로를 mock으로 조용히 바꾸지 않았다.
E03 모델 없이 가능한 탐색/조회/선택/저장에 불필요한 AI 호출을 추가하지 않았다.
E04 예상 밖의 외부 요청·중복 세션·인증 우회·원본 데이터 삭제가 없다.
E05 키·토큰·사람 영상·비공개 DB/로그가 Git이나 최종 보고에 노출되지 않는다.

검수용 지연/오류 입력:
- 상의 A 적용 응답이 B 선택 뒤 도착
- 라벨 없는 다른 옷 진입
- 위치 unknown
- 같은 선반의 두 옷을 포함한 코디
- 저장 성공 뒤 응답 유실
- 사용자 전환 직후 늦은 읽기/피팅 응답
- 화면을 떠난 뒤 늦은 stream 연결 성공

단위검사/빌드 통과와 실제 브라우저 시나리오 통과를 구분해 보고한다.
실제 터치 기기가 없으면 포인터 시뮬레이션과 마우스 검수로 적고 '실물 터치 검증 완료'로 쓰지 않는다.
실제 API·영상 품질을 시험하지 못했으면 해당 검사는 NOT RUN/BLOCKED다. 0회 실행을 성공으로 세지 않는다.

================================================================
14. 자는 동안의 작업 보존·중단 복구·최종 보고
================================================================

사용자는 중간에 응답하지 않는다. 이 지시 범위 안에서는 자율적으로 구현→실행→검수→수정한다.
도구/세션/승인 제한을 우회하거나 무한 실행을 만드는 작업은 하지 않는다.
계속 작업할 수 있는 동안은 계획 보고에서 멈추지 않되, 실제 제한에 도달하면 안전한 checkpoint를 남긴다.
이 지시만으로 밤새 실행·자동 재개가 기술적으로 보장되는 것은 아니다.

프로젝트 안에 작업 로그 한 개(예: tasks/mirror-ux-rebuild-progress.txt)만 간결하게 유지한다:
- 실제 작업 branch/실행 주소·명령
- 완료한 단계와 수정 파일
- 검사 실행/결과/미실행 사유
- 미결정/차단된 작업과 독립적으로 계속한 작업
- 다음 시작점
문서 복제·새 PRD·새 통합설계서는 만들지 않는다.

단계별 안정된 변경은 관련 파일만 commit한다.
기준 사진/생성 파생자산의 공유 권한을 확인한다. 사용자 비공개 미디어/키는 제외한다.
GitHub 목적지가 이미 확인돼 있고 자동 운영배포가 없으면 작업 branch로 push한다.
권한·remote가 불명확하면 추측해 새 public repo를 만들지 않는다. 로컬 commit과 remote 미완료를 구분한다.
세션이 재개되면 원본을 다시 만들지 말고 checkpoint·현재 파일·Git diff를 보고 이어간다.

최종 제공:
1. 실행 명령과 실제 열어야 할 주소, 현재 실제 데이터/피팅 모드
2. 기준 배경 OFF와 한 구역 ON, 여러 구역 ON 캡처
3. 김수진: 탐색→이력→라벨→위치 유지의 실제 브라우저 녹화
4. 최휘재: 홈→전체 비교→상의 교체→오늘 기록/LED→재조회의 실제 브라우저 녹화
5. 동일 크기의 수정 전/후 비교(현재 코드 화면 vs 기준 사진, 허용 변경 영역 구분)
6. 실제 검사 결과와 남은 제약(자산/권한/API/실물 검증을 별도로 표시)
7. 보존한 연결·데이터, commit hash, 원격 push/배포 미실행 상태

핵심 과업이 끝나지 않았으면 '완료' 대신 어느 장면까지 작동하는지 정확히 적는다.
'버튼을 눌렀다', '빌드됐다'만으로 미러 경험을 완성했다고 보고하지 않는다.

지금 시작하라.
설계서·기준 사진·기존 연결을 보존하면서, 실제로 실행되는 미러 장면과 두 사용자 경험을 완성하라.
