## 1. 목적과 확정 결정

기존 Digital Twin·의류 관리·VTON 백엔드를 최대한 재사용하면서 실제 보유 의류 데이터를 초기 적재하고, 쇼핑몰 화면의 **구매 내역** 및 **좋아요** 기능을 프론트와 통합하여 QA·시연한다.

| 항목 | 설계 결정 |
|---|---|
| 쇼핑몰 사용자 기능 | **구매 내역 조회·선택 가져오기**, **좋아요 목록 조회·VTON 입어보기**만 포함 |
| 이번 범위 제외 | 장바구니, 최근 본 상품의 화면·API·Mock fixture·QA 시나리오 구현 제외 |
| 연동 방식 | 실제 쇼핑 플랫폼 인증·제휴 API 대신 **Mock Shopping Provider** 사용. 실제 제휴 연동인 것처럼 표현하지 않음 |
| 사용자 입력 | 상품 URL 직접 입력을 핵심 UX로 채택하지 않음. URL은 상품 식별·출처 추적용 내부 데이터 |
| 초기 의류 데이터 | 사용자 제공 실제 보유 의류 URL **입력 10건, 고유 상품 주소 9개**를 검토 대상에 포함 |
| 우선 적재 후보 | 사전 검토에서 필수 필드가 확보된 **입력 1·3·4·10의 4개**부터, 사전 조건 충족 후 단계적으로 적재 |
| 나머지 데이터 | 충돌·미확인·추출 실패를 해결한 후 후속 적재. 영구 제외 아님 |

| QA·시연 확장 | 초기 데이터 외 추가 상품·시나리오를 추후 보강 가능. 실제 소유·실제 쇼핑 활동과 합성 기록을 명시적으로 구분 |
| 실행 승인 | 이 문서 자체는 DB 쓰기·이미지 업로드·동의 변경을 승인하지 않음 |

## 2. 핵심 사용자 플로우

### SF-01 — 구매 내역 → 내 옷장 가져오기

1. 쇼핑몰 탭에서 Mock Provider가 제공하는 구매 내역을 조회한다.
2. 상품명·브랜드·이미지·선택 옵션·수량 및 확인 가능한 구매 상태를 표시한다.
3. 사용자가 가져올 상품을 선택하고 **실제 보유 여부·실물 수량·소유자·옵션**을 확인한다.
4. 백엔드가 상품 카탈로그, 원본 구매 항목, 기존 보유 의류 및 적재 원장을 대조해 중복을 검사한다.
5. 확인된 실물 개체마다 `garment`를 생성하고 원본 상품·구매 항목과 연결한다.
6. 내 옷장과 Digital Twin에 반영한다. 위치·RFID·착용·세탁 이력은 근거 없이 생성하지 않는다.

**구매 기록만으로 실제 보유를 확정하지 않는다.** 배송·취소·반품 및 현재 보유 여부를 구분한다. 이번 사용자 제공 10개 URL은 실제 보유 목록이지만, 그 URL만으로 특정 쇼핑몰에서 구매한 이력까지 증명되지는 않는다. 시연용 구매 기록이 필요하면 **합성 Mock 구매 이력**으로 표시한다.

### SF-02 — 좋아요 → VTON 입어보기

1. 쇼핑몰의 **좋아요** 목록에서 상품을 조회한다.
2. 선택한 상품 또는 옵션을 VTON 입력으로 전달한다.
3. 기존 VTON 세션·비동기 작업·결과 자산 흐름을 가능한 한 재사용한다.
4. 결과를 확인한다. 좋아요·VTON 실행은 `garment` 등록 또는 실제 착용(`wear_event`)으로 기록하지 않는다.

**이번 범위에서는 좋아요 상품의 저장 코디·코디카드 포함 여부를 확정하지 않는다.** 해당 기능이 필수로 드러나면 별도 변경 결정으로 관리한다.

## 3. 데이터 모델 및 책임

| 엔터티 | 저장 내용 | 핵심 관계·제약 |
|---|---|---|
| `catalog_product` | provider, external_product_id, 브랜드, 상품명, 카테고리, 원본 URL, 이미지 참조, 확인된 소재·케어, 원본 메타데이터, 동기화 시각 | `(provider, external_product_id)` 고유성 검토. 상품 식별 정보는 원본 보존 |
| `catalog_variant` | 상품별 실제 확인된 색상·사이즈·옵션명 및 외부 옵션 ID(존재 시) | `catalog_product` 1:N. 확인되지 않은 옵션을 임의 생성하지 않음 |
| `shopping_connection` | 회원과 Mock Provider 연결, 동기화 상태 | 실제 계정 비밀번호·인증 토큰을 fixture에 저장하지 않음 |
| `shopping_purchase_item` | 구매 항목 참조, 상품·옵션, 구매·배송 상태, 수량, 동기화 시각, 가져오기 상태 | **Mock 기록과 실제 구매 증빙을 구분**; 가져오기 중복 방지 |
| `shopping_activity` | **LIKED** 활동, 회원·상품·옵션 참조, 원본 기록 및 동기화 시각 | 이번 범위의 활동 유형은 LIKED만 사용. 구매는 별도 purchase 모델 |
| `garment` | 실물 보유 의류의 소유자, 상품/옵션 연결, 위치·상태·착용·관리 관련 정보 | `catalog_product` 1:N `garment`. 같은 상품 두 벌이면 `garment` 두 개 |
| `asset` | 검증된 비공개 이미지 자산 | 외부 이미지 URL과 READY 상태의 내부 `asset_id` 구분 |
| `garment_import_source` 또는 동등한 연결 구조 | `garment` ↔ 상품·구매 항목·원본 키·적재 실행 기록 | 재시도·출처 추적·부분 실패 복구 지원. 구체 모델은 최신 코드 확인 후 결정 |

기존 DB에서 `garment.name`, `garment.attributes`가 존재하더라도 등록·조회 API에서 노출되지 않는 것으로 사전 검토되었다. **최신 Sprint 7 코드·마이그레이션을 먼저 재확인**하고, 상품명·브랜드·출처·옵션이 UI/API에서 손실 없이 조회되도록 필요한 DTO·서비스·OpenAPI를 비파괴적으로 확장한다.

### 1차 적재 선행 조건

- 대상 **회원/가구 및 `owner_id`** 확인; 임의 데모 계정 자동 선택 금지.
- 후보 4개가 실제 보유 중이며 **각각 몇 벌인지**, 기존 DB에 등록돼 있는지 확인.
- 상품 카탈로그·보유 의류 연결 계약 및 필요한 마이그레이션 검증.
- 이미지 사용 여부, 이용 조건, 사용자 업로드 동의 및 MinIO 처리 방식 확정.
- 승인된 적재 목록·고정된 요청 본문·중복 방지 원장 준비.

**4개 우선 적재는 권장 실행 순서이지, 이 문서로 실제 등록을 승인한 것은 아니다.**

## 5. 적재 파이프라인

```text
사용자 제공 상품 URL / 검증된 원본 자료
       ↓
URL 정규화 · 상품 식별 · 메타데이터 검증
       ↓
카탈로그 및 옵션 Upsert (출처·검증 상태 기록)
       ↓
실제 보유 확인 · 소유자/수량/옵션 확인 · 기존 의류 중복 대조
       ↓
[이미지 사용 승인 시] 다운로드/검증 → MinIO 업로드 → READY 확인
       ↓
기존 등록 API 또는 승인된 확장 API로 garment 실물 단위 생성
       ↓
원본 상품·구매 항목·garment_id 연결 및 적재 원장 갱신
       ↓
내 옷장 UI · Digital Twin 조회 및 QA
```

쇼핑몰 Mock 구매 이력 fixture 생성과 **실제 보유 의류의 DB 적재는 별개 작업**이다. 사용자 제공 URL을 구매 이력·좋아요 기록으로 자동 분류하지 않는다. 좋아요 fixture의 대상 상품은 별도 시연 시나리오로 선정한다.

### 중복·재실행·부분 실패

- 상품 키 예시: `tonywack:4903`, `lmood:3247`, `musinsa:<상품번호>`.
- 같은 상품을 여러 벌 보유할 수 있으므로 상품 키만으로 실물 의류를 합치지 않는다.
- 적재 원장에 소유자·상품 키·옵션·실물 개체 키·`garment_id`·`asset_id`·단계 상태를 기록한다.
- 각 등록 요청의 `Idempotency-Key`와 고정된 요청 본문을 보관한다. 동일 요청 재시도는 동일 키를 사용한다.
- 재시작 시 DB/API와 원장을 대조한 뒤 이어가며, 성공·보류·실패를 항목별로 구분한다.
- 적재 원장 제안 경로: `data/imports/owned-garments-2026-10-09.json`. 비밀키·토큰·서명 URL은 저장하지 않는다.

## 6. 이미지 및 MinIO 정책

- 외부 상품 이미지 URL은 출처 참조이며, 내부 `image_asset_id`가 아니다.
- 이미지 저장이 승인된 경우 기존 `purpose=GARMENT` 업로드 intent → 서명 PUT → SHA256 finalize → READY 확인 절차를 준수한다.
- JPEG/PNG/WebP, 10MiB 이하, 한 변 4096px 이하 등 기존 검증 조건을 유지한다.
- 비공개 `wardrobe-assets` 버킷을 사용하고 공개 버킷을 임의 생성하지 않는다.
- 상품 참고 이미지(`CATALOG_REFERENCE`)와 실제 촬영 이미지의 출처를 구분한다.
- 이미지 이용 조건 및 업로드 동의를 확인한다. 동의가 없으면 자동 변경하지 않는다.
- 이미지 다운로드·검증·업로드 실패 시 이미지 포함 등록을 보류한다. 이미지 없는 등록은 별도 승인 후 실행한다.

## 7. API 및 프론트 통합 변경 요구

아래 경로는 **후보**이며, 실제 경로·DTO는 최신 `06_OPENAPI.yaml` 및 Sprint 7 구현과 충돌 검토 후 확정한다.

| 기능 | 후보 API/변경 | UI 인수 조건 |
|---|---|---|
| 쇼핑몰 구매 목록 | `GET /api/v1/shopping/items?type=PURCHASED` | 구매 내역·상품·옵션·보유 확인 상태 표시 |
| 쇼핑몰 좋아요 목록 | `GET /api/v1/shopping/items?type=LIKED` | 좋아요 상품 목록과 VTON 진입 |
| Mock 동기화 | `POST /api/v1/shopping/sync` | 동일 fixture 반복 동기화에도 중복 없음 |
| 선택 가져오기 | `POST /api/v1/shopping/import-purchases` | 확인된 개체만 등록, 항목별 성공/보류/실패 표시 |
| 상품 카탈로그 | 조회 DTO 및 원본·옵션 매핑 추가 검토 | 브랜드·상품명·이미지·색상 등 필요한 정보 표시 |
| 의류 등록·조회 | 기존 `garment` API 최소 확장 | 카탈로그 연결·상품명·출처·옵션 정보 보존 |
