# Smart Wardrobe — 가구·의류·공간·에셋 시연 데이터 설계안

- 문서 ID: `SW-SEED-DESIGN-001`
- 버전: v0.1 / 상태: **협의용 제안, 확정·적재·구현 승인 아님**
- 연계: `SW-INTEGRATION-CHANGE-001`의 CHG-00(DB 적재), CHG-08(동적 옷장), CHG-09(보관 에이전트), `SW-CARD-TEMPLATE-001`
- 기준: 2026-10-11 사용자 제공 옷장 화면, T1–T4 원본 및 계약서
- 중요: 이 문서는 실제 프로젝트 DB/FSD를 대조하지 않은 **논리 시드**이다. 필드/테이블 신설 또는 실제 이미지 제작을 승인한 것이 아니다.

## 1. 제품 목적 → 데이터 설계 원칙

- 핵심 페르소나: **가족의 의류를 통합 관리하며 계절 전환·보관 공간 관리에 부담을 느끼는 엄마**.
- 실사용 장면의 배우: **엄마와 아들**. 다른 가족 구성원이 화면에 등장할 필요는 없다.
- 가구 규모는 **4인 가구(엄마·아빠·아들·딸)를 제안**하며 최종 확정은 사용자 판단. 가족 수와 시연 등장인물 수를 혼동하지 않는다.
- 공유 물리 옷장 1대가 의류 관리의 관문이지만, 모든 의류가 그 옷장 안에 있는 것은 아니다.
- 옷장에서 눈에 보이는 의류는 실제 아이템 레코드와 1:1 관계. 화면용 가짜 옷은 사용하지 않는다. 원본 이미지와 수납용 파생 이미지는 구분한다.
- 주요 코디·시연 대상 의류는 높은 이미지 재현도를, 배경 의류는 DB 일관성을 우선하되 시각 품질 평가를 별도로 수행한다.

## 6. 가족·권한 모델

- `household_id`: 공용 계정/가족 데이터 경계.
- `member_id`: 의류 실소유자(엄마·아빠·아들·딸 예시). **엄마·아들이 UI 시연 중심**이다.
- `device_id`: 현재 공용 스마트 옷장 기기. 구성원 수 또는 소유자 수와 혼동하지 않는다.
- `item_id`: 의류 및 소품의 불변 논리 식별자. 의류 전용 테이블만 있다면 소품 모델을 현재 스키마와 대조한다.
- `shared_use_policy`: 가족 소유라도 다른 구성원의 코디 추천·피팅에 사용할 수 있는지 명시. 엄마의 아이템을 아들이 빌려 쓰는 경우 `owner_member_id`는 유지하고 코디 사용 주체를 구분한다.
- `current_location`: 외부 공간과 실물 옷장 모두 동일한 위치 모델을 사용한다.

## 7. 시연 시나리오와 데이터 연결

### SCN-01 엄마: 계절·보관 부담 감소
1. 사용자: 엄마 프로필 선택. 가족 의류 전체 위치를 확인.
2. 입력: **고정된 데모 날씨 예보**(기온 하락) + 가족 소유 계절 태그 + 각 보관함 환경·여유 공간. 날짜와 `source=mock` 명시.
3. 제안: `M01(A1) → BOX-BED-01`, `S04(B4) → BOX-UTIL-01`, `D04(F4) → BOX-UTIL-01`의 반출과 `M12 → A1`, `S14 → B4`, `D08 → F4`의 회수. 각 이동은 공간 수용량·아이템 적합성 확인 후 묶음으로 제안.
4. 엄마가 **제안 수락**해도 DB 현재 위치는 유지. 옷을 실제로 옮기고 **일괄 이동 완료 확인**했을 때만 위치와 화면이 갱신.
5. 옷장 이미지는 반출/회수 3개 슬롯이 바뀌고 옷 찾기/LED 위치도 새 위치를 가리킴. 외부 공간에는 조명 명령을 보내지 않음.
6. 환경 경고가 있다면 센서 출처·시각·Mock 여부와 공간별 특성을 보여주되, 권한/장치가 확인되지 않으면 제습기 작동 성공을 주장하지 않음.

### SCN-02 아들: 코디 → AI 입어보기 → 의류 찾기 → 카드
1. 아들 프로필 선택, 홈에서 **2~3개 추천 코디 캐러셀**.
2. 추천은 모두 가족이 소유·등록한 아이템 중 접근 가능한 것만 사용. 예시: `S03+S11+S06+A03`, `S05+S07+A02+A05`, `S14+S12+S08+A03+A06` (S14는 SCN-01에서 실제 회수 완료된 경우만 현재 옷장에 표시).
3. 카드 선택 → **AI 입어보기**: 지원 API와 권한 확인 후 카메라 또는 사진 방식으로 실행. 실행 전후 옷 조합 ID 보존.
4. **이 코디 입기**는 착용 확정 및 필요한 물리 구획 안내·Mock LED 점등. `actual_worn_at`은 생성하지 않음.
5. 사용자가 별도로 **코디카드 만들기**를 선택 → T1–T4 중 호환 템플릿 선정 → 등록된 원본/파생 에셋으로 PNG 생성. 코디카드는 VTON 결과를 카드 소재로 자동 대체하지 않음.
6. 다른 구성원 옷을 빌려 쓰는 흐름은 `shared_use_policy`가 허용할 때만 시연한다.

**코디카드 템플릿별 실제 DB 매핑 후보:**
- `T1` 엄마: M08 버건디 니트 + M06 블랙 슬랙스 + A01 앵클부츠 + A04 토트백.
- `T2` 아들: S03 블루종 + S11 블랙 니트 + S06 생지 데님 + A03 워커 + A08 크로스백.
- `T3` 아들: S14 숏패딩(회수 후) + S12 올리브 니트 + S08 슬랙스 + A03 워커 + A06 볼캡 + S16 장갑(보관함 위치 안내).
- `T4` 아들: S05 네이비 후드집업 + S07 블랙 데님 + A02 스니커즈 + A05 백팩 + A06 볼캡.

템플릿별 필수 소품 슬롯과 레이어 호환성은 T1–T4 원본을 실제 분해한 이후 확정한다. 디자인상의 카테고리 교체가 원본 조형과 충돌하면 다른 등록 아이템을 선택하거나 해당 템플릿을 보류한다.

### SCN-03 엄마: 특별 관리 의류 찾기
- `M02(차콜 울 롱코트)` 검색 → A2 표시 → A구획 Mock LED → 소재·케어라벨 확인 기반 가이드. 제습기·환경 제어는 별도 승인/기기 지원 여부 검증.

## 8. 이미지 에셋 계층 및 작업량 제어

| 에셋 종류 | 목적 | 제작 원칙 |
|---|---|---|
| `source` | 상품 정면/실물 원본 | 아이템당 1개 이상, 출처·라이선스·색상 검수 |
| `catalog-cutout` | 의류 목록·추천·코디카드 | 배경 제거, 원본 색상/로고 보존 |
| `hanger-view` | A/B/C 옷장 내부 | 원근·수직 높이·겹침 규칙에 따라 반측면/걸린 상태 파생. 필요한 품목만 제작 |
| `folded-view` | D/E/F 선반 | 접힘 형태 파생. 품질 부족 시 슬롯별 보수적 렌더/수동 검수 |
| `card-retargeted` | T1–T4 각 독립 레이아웃 | 템플릿별 마스크/변환 기반. 범용 단일 템플릿으로 대체 금지 |
| `rendered-card` | 최종 PNG | 템플릿·아이템·파생 에셋 버전 스냅샷 저장 |

모든 파생 이미지는 `item_id/source_asset_id/derivation_method/quality_status/version`으로 원본과 연결한다. 키 품목(두 시연의 추천·이동·카드 대상)을 먼저 제작하고, 나머지로 옷장 질감과 밀도를 채운다. **한 장의 원본 사진만으로 진짜 옷의 측면·접힘 형태를 정확히 복구할 수 없으므로 생성 결과는 실제 촬영이라고 표시하지 않는다.**

## 9. 논리 데이터 관계 및 감사조건

`household → members + devices → spaces/compartments/slots`;
`household → items(owner_member_id, category, season, material, share_policy)`;
`items → assets(source, derived) + current_location + movement_history`;
`outfit(member_id, items[]) → VTON session / confirmation / card job`;
`location → light_zone`;
`recommendation → evidence(snapshot of forecast, environment, capacity, garments) → proposal/acceptance → completion`.

검증:
1. 각 아이템은 한 시점에 1개의 실제 현재 위치만 가진다. 사진에 보이는 옷장 아이템은 `A..F` 슬롯의 DB 레코드와 1:1로 대응한다.
2. 35개 시각 아이템 + 외부 의류 8개 + 소품 8개 = 총 51개 레코드. 초기 외부 공간과 추가 현관 공간의 위치 및 용량을 검증한다.
3. 시연 추천의 모든 아이템 ID가 존재하고, 사용 권한·카테고리·이미지·템플릿 슬롯 적합성을 통과해야 한다.
4. 이동 제안 승인 상태와 실제 이동 완료 상태를 분리하며, DB·검색·화면·조명 매핑이 완료 전후 각각 일관되게 동작해야 한다.
5. 코디 선택·카드 생성·VTON 완료·실제 착용 기록은 서로 다른 이벤트다.
6. 이미지 URL의 만료 여부와 관계없이 영속 DB에는 `asset_key` 등 지속 식별자만 저장한다.
7. 기존 실제 스키마·FSD와 충돌을 확인하고, 사용자 승인이 나기 전에는 데이터 마이그레이션/시드 실행/이미지 대량 생성 금지.

## 10. 승인할 결정 (딱 3개)

1. 4인 가족 DB(엄마·아빠·아들·딸) + 엄마·아들 2인 시연 배우 설정 승인 여부.
2. 첫 데이터셋 규모: 옷장 35 + 외부 의류 8 + 소품 8 = 총 51개 승인/축소 여부.
3. 외부 공간: 침실 보관함, 다용도실 보관함, 현관 신발장/수납장 및 공유 사용 권한 기준 승인 여부.
