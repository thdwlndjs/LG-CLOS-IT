# 옷장 원본 보존 · 상품 후보 및 배치 승인안

상태: **사용자 승인 대기**. 현재 구현 화면의 시각 품질은 사용자가 승인하지 않았다. 이번 산출물은 상품 후보와 원본 좌표 기반 배치 계획이다. 앱 코드·DB·실행 에셋·배포는 변경하지 않았다.

요구 해석: Codex가 의류를 바꾸기 전 팀원 원본의 카메라·옷걸이 방향·중첩·옷자락 길이·행거 간격·접힌 옷의 측면·선반 적층 규격을 보존하고 상품 정체성만 바꾼다. 휘재가 시연의 주인공이며 왼쪽을 주로 사용한다. 오른쪽에는 다른 가족의 의류를 배치한다. 전체 작업은 후보와 배치 승인 이후 진행한다.

- [배치도](placement.png), [상품 후보 사진판](candidate-board.png), [조명 연출안](led-concept.png).
- [상품·위치 계획 원본 데이터](proposal.json): 공식 상품 URL·사진 출처·파일 해시·제안 소유자·좌표·미적재 상태.

사진판의 상품 사진은 공식 카탈로그 참고 자료다. 배치도에 보이는 의류는 변경 전 원본이며, 새 상품으로 교체한 합성 결과가 아니다. 이번 단계에서 교체 에셋을 생성하지 않았다. 조명 버튼은 이 보고서 안의 CSS 연출이며 실제 LED 검증이 아니다.

## 의류 찾기와 조명

시연: 휘재 선택 → 데님 셔츠 검색 → B3 위치 안내 → 원본 조명 위치에 있는 상단 B 영역의 따뜻한 불빛 → 안내 종료 시 소등. B3와 C6 에크루 바지를 함께 선택하는 코디에서는 각 승인된 위치의 Mock LED만 작동하도록 연결한다. 전체 옷장 점등은 하지 않는다. 원본 조명점과 DB slot/controller channel의 대응은 별도 매핑 확인 대상이며 이 시안이 실제 하드웨어 채널 존재를 증명하지 않는다. 매장 원격 차단·위치 불확실 시 미점등 계약은 유지한다.

## 수량 및 데이터에서 남은 사항

원본을 눈으로 읽은 구조는 행거21 + 오른쪽 접힌66 + 왼쪽 아래 접힌6 = **93개의 시각적 의류 자리**다. 현재 격리 DB의52개와 같지 않다. 33개 후보는 전체93개 등록 목록이 아니다. 현재 상품을 무조건93개로 늘리거나 같은 상품/의류 ID를 여러 위치에 반복 적재하지 않는다.

승인 후 접힌 의류72자리(오른쪽66+왼쪽 아래6)의 개별 상품/색상/제안 소유자 배정을 완성해야 한다. K1~K12는 스타일 검토용 대표 후보이며 72자리를 반복 복제로 채우는 목록이 아니다. 최종 데모 등록 수량과 대체 대상은 그 매핑에서 명시한다. 실제 보유 의류·기존52개·새 데모 후보를 구분하고 기존 기록을 삭제하거나 소유자를 바꾸지 않는다. 새로운 상품을 가족이 실제 구매했다는 사실·착용·세탁 이력은 생성하지 않는다. 선반당6벌의 위치·용량과 현재 슬롯 정의가 맞는지도 적재 전에 검토한다. 이번 단계에서는 schema/API/slot capacity를 변경하지 않았다.

## 승인 후 작업과 인수 기준

이번 승인 대상은 후보33개와 배치·스타일 방향이다. 승인을 받으면 이 방향으로 나머지 상품 선정과 원본을 따르는 교체 에셋 작업을 진행한다. 이 승인을 임의 DB 수량 확대·기존 데이터 삭제·운영 변경 허가로 간주하지 않는다. 최종 등록 목록에서 미확정 수량/대체 범위를 먼저 구체화한다.

1. 승인된 상품 방향/배치에 따라 선반 전체 상품 매핑과 데이터 변경 계획을 완성한다.
2. 원본 A/B/C 각 옷걸이와 D/E/F 각 적층 모양을 따라, 상품만 교체하는 위치별 에셋을 만든다. 새 배경 전체를 재생성하지 않는다.
3. 원본과 교체 결과를 같은 크기로 비교한다. 각도·겹침·길이·틈·선반 바닥 접점이 다르면 다시 만든다. 선반은 실제로 2묶음×3층이어야 한다.
4. 기존 API/DB/MinIO 계약을 유지하며 승인된 최종 매핑을 적용하고, 의류 찾기·Mock LED·프로필 전환·목록/이미지 정합성을 검증한다.

자동 파일검사 통과는 사용자 시각 인수를 대신하지 않는다. 현재 생성 sprite 커밋 `a4e13f3`의 외형은 승인되지 않았으며 이 승인안의 원본 기준이 우선한다. DB 적재, 앱 반영, 원격push, 배포는 이번 단계의 완료 범위에 포함하지 않는다.
