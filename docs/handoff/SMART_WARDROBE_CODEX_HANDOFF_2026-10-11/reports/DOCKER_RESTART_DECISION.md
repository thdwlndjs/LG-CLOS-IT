# 기존 Docker Desktop 정상화 판단

2026-10-12. 사용자 지시에 따라 별도 Docker Engine 구축을 중단했다. 이번 단계는 기존 증거와 프로젝트 자산의 대조만 수행했으며, 재시작·신규 환경 구축·적재는 실행하지 않았다.

## 판단

**기존 Docker Desktop 재시작을 다음 승인 대상으로 권고한다.** 핵심 시연 데이터는 재구성할 수 있고, 현재까지 추가로 회수 가능한 최신 live 데이터는 발견하지 못했다. 다만 모든 namespace·외부 핸들에 대한 완전한 배제가 아니므로 추가 손실 가능성이 절대0이라는 보장은 하지 않는다.

이전 재시작 보류의 주된 이유였던 PG/MinIO live tmpfs 보존 위험은 실측으로 낮아졌다. 원래 컨테이너 cgroup에 프로세스가 없고 anon/file/shmem/swap도0이었다. 접근 가능한 프로세스 namespace·열린 핸들에는 데이터 마운트가 없었다. Redis도 실행 cgroup이 비어 있었고 영속 RDB만 확인됐다. 이를 최초 촉발 원인 확정이나 최신 데이터 전역 소실 확정과 혼동하지 않는다.

## 회수된 데이터와 실제 손실 판단

영속 볼륨 복구 후보는 독립 Windows 작업본에서 실제 기동·SQL/객체 읽기·논리 dump/별도 DB 복원 시험을 통과했다. 의류9·사용자2·에셋7·코디16·카드1·Job1·감사119를 회수했고 FK 고아0이다. MinIO9객체는 모두 이미지 읽기 검증을 통과했고 DB READY에셋7개와SHA256이 일치한다. 이 기존 기록은 재구성 후에도 보존한다.

승인104벌 ID와 회수9벌 ID의 교집합0. 회수사용자2명의 ID도 승인시연프로필2명과 다르다. 따라서 승인household104와 회수household9를 함께 보존하면 전체113벌이 된다. 수량을104로 맞추기 위한 기존9벌 삭제/재할당은 금지한다.

**그대로 복원하지 못하는 범위:** 최신 tmpfs DB의 전체 상태, 승인 시연 데이터 생성 이후 사용자 변경, 최신 C단계 Snapshot/Job/결과 연결, 그 기간의 카드·공유 토큰·세션·동의·감사/권한 상태. 파일로 따로 남아 있는 결과물은 활용 후보지만 DB 연결과 이력의 정확한 원복은 보장하지 않는다. 정확한 손실 건수는 최종 시점의 완전한 DB 백업이 없어 산정 불가다. 승인된 합성 wear108건·LIKED6건은 재생성 가능한 누락분이며 실제 사용자 이력 손실 건수로 세지 않는다. 실제 FitRoom 유료 호출은 기존 검증 기록상0회이며 권한/소진 상태를 임의로 되살리지 않는다.

## 재시작으로 추가 유실 가능한 데이터

- 확인된 최신 live PostgreSQL/MinIO 데이터: 없음. cgroup 및 메모리·마운트 실측상 원래 실행 상태가 이미 사라져 있다.
- 확인된 Redis live 메모리: 원래 cgroup에 없음. RDB는 영속 디스크에 존재하며 일반 재시작은 볼륨 삭제 동작과 다르다. RDB 내용의 백업/무결성 검증까지 완료한 것은 아니다.
- 기존 영속 PG/MinIO: 최초 복사본과 검증된 논리 dump/객체 회수 자료를 별도 보유. 재시작 시 journal/WAL 복구 또는 자동 기동으로 원본 상태가 달라질 가능성은 있지만 회수 자료는 호스트에 분리돼 있다. 기존 볼륨에 복사본을 덮어쓰지 않는다.
- 다른 프로세스/namespace의 미발견 잔존 데이터: 완전히 배제하지 못함. 따라서 무손실 보장 대신, 현재 실측과 검증된 회수본을 근거로 재시작의 잔여 위험을 수용하는 결정을 제안한다.

**현재 알려진 증거만으로는 추가 회수를 위해 재시작을 계속 미뤄야 할 구체적 대상이 없다.** 정확한 역사적 손실 규모와 잔존 가능성의 불확실성은 남기되, 핵심 시연 정상화는 재구성으로 진행할 수 있다.

## 승인 후 정상화 순서

1. Docker Desktop 재시작만 별도 승인받는다. WSL 전체shutdown·factory reset·prune·볼륨삭제는 포함하지 않는다. 재시작 전 호스트 회수본 및 논리 dump의 존재/해시를 확인한다.
2. Engine 응답과 기존 컨테이너/볼륨 상태를 읽기 전용으로 확인한다. 자동 기동 여부도 확인한다. 기존 tmpfs 컨테이너에 새 시드를 넣지 않는다.
3. 기존 영속 볼륨은 보존하고, 정상화된 Engine에 별도 프로젝트/새 named volumes를 사용하는 시연 스택을 구성한다. 별도Engine 구축은 하지 않는다. 준비된Compose의 영속저장 구조는 재사용하되 SSH독립Engine 전용 planner는 이번 경로에서 그대로 실행하지 않는다.
4. 회수 데이터와 객체부터 새 시연 볼륨에 복원하고 참조/해시를 검증한다. 최신0006마이그레이션은 새 대상에만 적용하며 회수기록 불변을 검증한다.
5. 승인104인벤토리를 기준으로 프로필·기기·위치·원본/파생asset·의류·Scene·합성Context/착용·LIKED의 누락분을 멱등 적재한다. 과거asset ID 연결이 불완전한 항목은 구체적 매핑으로 해결하고 승인manifest/geometry를 임의 변경하지 않는다.
6. 신규스택의 API/두프로필/Scene66+21/이미지/Mock VTON/코디카드 회귀, 신규컨테이너 재생성 후 데이터 유지, 백업 및 독립복원 시험을 수행한다. 실제 유료호출은 차단한다.
7. 실제 앱 접속/환경변수 연결 전환은 구체적인 대상과 변경안을 별도 승인받고 실행한다.

재시작 승인만으로 모든 기존 컨테이너 재생성·원본 볼륨 변경·실서비스 전환이 허용되는 것으로 해석하지 않는다. 이번 조사에서 재시작은 실행하지 않았다.
