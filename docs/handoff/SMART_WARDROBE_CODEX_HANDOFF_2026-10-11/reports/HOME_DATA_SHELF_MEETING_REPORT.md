# 홈 추천·관리제안·시연 데이터·오른쪽 선반 진단 및 회의 결정안

2026-10-11 · 브랜치 `feat/handoff-p3-p10` · 조사 기준 커밋 `0310a37`.

**현재 앱은 승인 행거 에셋 연결과 API 경로 검증은 했지만, 요청한 초기 홈과 완성된 가족 옷장 시연에는 도달하지 못했다.** 오늘의 추천은 생성된 코디카드가 아닌 상품 사진 조합이고, 실제 추천은 자동 실행하지 않는다. 홈 관리추천은 착용 로그가 없어 전량 보류한다. 오른쪽은 전체 배치가 아닌 접힌 샘플3개만 연결해 수량과 바닥 접점이 부족하다. 이 상태를 최종 시연 완료로 볼 수 없다.

이번에는 조사·보고만 했다. 제품 코드, 상품·착용·위치 데이터, 에셋, 계약은 수정하지 않았다. 브라우저 확인을 위한 데모 인증 세션 외에 추천/이동/카드 생성 요청도 실행하지 않았다. 보고서·증적만 로컬 커밋하며 push/배포는 하지 않는다.

## 1. 이번 지시에서 확정된 요구와 조사 범위

- **오늘의 코디 추천은 실제 코디카드 이미지로 표시한다.** 현재 상품 사진 나열은 목표 UI가 아니다.
- **초기 홈에서 사용 이력 영역을 제거한다.** 추천의 내부 입력으로 사용하는 로그 자체를 없애라는 뜻으로 해석하지 않는다. 이번에는 제거하지 않고 후속 구현 요구로 기록한다.
- DB에 사용 로그와 쇼핑 상품/구매 시연 데이터를 연결하여 현재 옷장 의류가 추천·관리에 실제 입력되게 한다. 화면 배열의 Mock 숫자를 DB 로그 대신 사용하지 않는다.
- 오른쪽 접힌 의류의 수량·적층·바닥 접점과 빈 공간을 해결한다. 전체 물량과 기존 상품 재사용 여부는 아래 회의 결정안으로 제시한다.

확인 환경은 로컬 앱 `http://127.0.0.1:5193`, API18081, **격리 PostgreSQL `wardrobe_test_remediation`**이다. 클라우드/운영 DB나 배포 UI를 이번에 확인한 결과가 아니다. 실제 브라우저에서 김수진 로그인 완료를 확인한 뒤 홈과 ‘실제 기록’을 열었다. 제품 데이터를 쓰지 않고 DB의 현재 입력으로 동일 보관 planner를 메모리에서 실행했다.

## 2. 코디추천이 원하는 형태로 작동하지 않는 이유

| 항목 | 확인한 현재 동작 | 원인 |
|---|---|---|
| 초기 홈 | `data-home-source=MOCK`, 구성형 미리보기3개 | `VITE_HOME_DEMO_SCENARIO`가 `off`가 아니면 표시용 겨울 시나리오가 기본이다 |
| 실제 기록 진입 | 후보0개, 추천 API 자동 호출0회 | candidates의 초기값은 빈 배열이다. 로그인/홈 진입 자동 조회가 없고 ‘내 옷 추천 받기’를 별도로 눌러야 한다 |
| 오늘의 카드 | `data-card-preview=composition` | 추천 응답을 프론트 Outfit으로 바꾸지만 `cardAsset`을 붙이거나 카드 생성·재조회하지 않는다 |
| 이미 저장한 카드 | 별도 목록에서는 서버 PNG 표시 가능 | backendClient의 저장 코디 목록에만 저장 cardAsset을 결합한다. 새 추천 후보와 저장 카드 목록은 별개다 |
| 추천 개인화 | 착용 완료 로그0건 | 서버는 이력이 없어도 cold-start 규칙으로 추천한다. 다만 최근 착용에 따른 회피/선호 반영이 비어 있다 |
| AI·날씨 | 규칙 추천, 요청 Context는 MOCK | OpenAI 미연결 때문에 추천 전체가 실패하는 것은 아니다. 서버 추천 엔진은 원래 결정적 규칙이고, 현재 날씨18°C Mock 입력과 홈 문구16→7°C가 서로 다르다 |

따라서 **착용 로그가 없어서 코디추천 API가 아예 불가능한 것은 아니다.** 2026-10-11 전차 양 계정 E2E에서 버튼으로 서버를 호출했을 때 각각 후보3개가 나왔다([해당 browser.json](evidence/remediation/browser.json), 조사 기준 커밋0310a37). 기존 카드 PNG의 김수진/최휘재 결과는 T1–T4 각각 파일 해시가 같아, 가족 공통 입력과 비어 있는 개인 이력에서 두 프로필이 같은 조합으로 나오는 개인화 부족도 확인했다. 이번 확인은 상품 데이터를 변경하지 않기 위해 생성 POST를 반복하지 않았다. 현재 문제는 초기 자동 조회, 생성된 카드 연결, 일관된 추천 입력 및 사용자 동작을 홈 흐름으로 완성하지 않은 것이다.

서버 규칙은 현재 Context 기온이15°C 미만일 때만 외투를 후보에 넣는다. 지금18°C Mock Context에서는 외투가 빠지고, 홈에 적힌 다음 주7°C 예보는 서버 입력에 전달되지 않는다. 프론트는 겨울 계절 constraint도 별도로 보내지 않는다. 따라서 추워지니 따뜻한 외투를 추천한다는 홈 문구와 실제 코디 결과가 맞지 않는다.

HANDOFF scene 모드의 실제 추천은 화면에 표시 가능한 승인24개로 후보를 제한한다. 신발·소품과 기존 숨김 의류는 제외되므로 보유76개 전체를 활용한 풍부한 코디도 아니다. 이 제한은 위치 찾기 시 보이지 않는 의류를 고르는 문제를 피하려고 추가했지만, 시연 데이터/장면 매핑을 완성한 해법은 아니다.

후속 구현 방향: 추천 응답 → 기존 `POST /cards/drafts` → render Job → `POST /cards/{id}/save` 및 카드 조회 경로 → 완료된 PNG를 오늘의 카드에 연결한다. 후속 구현 제안인 재사용 키는 프로필 ID·선택 의류 ID/버전·원본 이미지 asset ID/버전·템플릿이다. 이 구성 또는 이미지가 바뀌면 기존 결과를 재사용하지 않고 새로 생성한다. 아직 홈에서 구현된 캐시 동작이라는 뜻은 아니다. 홈에는 로딩·실패·빈 결과를 표시한다. 네 카드 템플릿 T1–T4의 원본 배치·접힘·가림 복원(Gate A)과 실제 의류 이미지 치환 품질(Gate B)이 현재 미완료이므로 PNG 연결만으로 카드 디자인까지 완성됐다고 판정하지 않는다. 홈 기본 템플릿은 회의에서 결정한다.

추가 정적 확인: 저장 카드의 `cardAsset`은60초 Signed URL을 직접 `<img>`에 넣고, 로딩 오류 시 구성형 사진 배열로 돌아간다. 의류용 Blob 캐시처럼 재발급·재시도를 연결한 경로가 아니다. 홈 코디카드에도 기존 asset ID 기반 이미지 캐시와 제한된 만료 복구를 적용해야 한다. 실제60초 만료 재현은 이번 조사에서 실행하지 않았으며, 이 항목은 코드상 확인한 후속 점검 사항이다.

## 3. 관리제안이 나오지 않는 직접 원인

홈의 ‘실제 보관 추천 조회’는 다음 입력이다.

`mode=WEAR_PATTERN / season=ALL / dry_run=true / analysis_window_days=90`.

서버의 해당 규칙은 **ALL 계절에서 착용 횟수0인 의류를 `INSUFFICIENT_WEAR_HISTORY`로 보류**한다. 현재 취소되지 않은 착용 완료 로그는0건이다. 동일 DB 입력과 실제 planner를 읽기 전용으로 실행한 결과:

| 사용자/호출 | 입력 범위 | 제안 | 보류 | 결과 |
|---|---:|---:|---:|---|
| 김수진 홈 ALL dry run | 가족76개 | 0 | 76 | NO_FEASIBLE_PLAN, 모두 INSUFFICIENT_WEAR_HISTORY |
| 최휘재 홈 ALL dry run | 접근 가능한 가족76개 | 0 | 76 | 동일 |
| 양 프로필 WINTER dry run | 동일한 가족76개 | 8 | 0 | ALL과 계절만 달리한 비교, FEASIBLE |
| 김수진 WINTER 실행 조건 분석 | 가족76개 | 8 | 0 | FEASIBLE |
| 최휘재 WINTER 실행 조건 분석 | 본인43개 | 4 | 0 | FEASIBLE |

WINTER 행은 **메모리에서 계산한 결과**이며 새 Job/제안/이동을 DB에 저장한 결과가 아니다. 계절만 바꾼 dry run은 두 프로필 모두76개 입력에서0→8건이므로 ALL 이력 보류와 WINTER 차이가 확인된다. 실행 조건에서는 OWNER인 엄마는 가족 관리, MEMBER인 아들은 본인 소유43개로 범위가 좁아4건이다. 홈 제안은 조회 가능한 가족 범위와 본인이 실행할 수 있는 범위를 구분해 표시해야 한다.

홈의 ALL 분석과 별도 ‘겨울 보관·회수 제안 만들기’ 버튼은 입력이 다르다. 후자는 WINTER로 보내므로 착용 이력이 없어도 명시적 계절 분류로 제안할 수 있다. 현재 계절·보관 상태·위치·용량 데이터가 전혀 없는 것은 아니다. 위치 관측114개와 합성 환경 데이터65행이 있다. 그러나 프론트 ‘두 번째 방 습도45%’ 문구는 화면용 상수이고 이 DB 분석 결과를 해설한 것이 아니다.

추가 구현 차이: 홈 분석은 수량/diagnostics 위주로 표시하고 의류명·추천 방·습도 비교·이동 이유가 연결된 관리카드를 만들지 않는다. `WEAR_PATTERN`은 계절/착용 기준이며, 방별 습도 최적화를 원하는 경우 기존 `SPACE_ENVIRONMENT` 입력·소재 케어 제약·환경 시각까지 연결해야 한다. 계절 추천에 날씨 예보를 연결하는 흐름도 아직 없다.

**OpenAI API 추가만으로 해결되지 않는다.** 먼저 DB 로그와 환경/계절 입력, 두 호출의 정책, 결과 UI를 연결해야 한다. 자연어 설명 생성에 OpenAI를 사용할지는 그다음 결정할 사항이다. 핵심 추천의 성공/실패와 LLM 설명 실패는 분리하는 것이 적절하다.

## 4. DB에 무엇이 있고 무엇이 없는가

| 데이터 | 현재 격리 DB | 의미 |
|---|---:|---|
| 의류 | 76개 = 기존52 + 승인24 | 원본 상품 사진·소유자·위치/상태 연결. 실제 구매 증명이 아닌 합성 시연 의류 |
| 취소되지 않은 착용 완료 | 0건 | 추천/관리의 사용 빈도 입력이 비어 있음 |
| 케어 완료 | 0건 | 관리 완료 이력도 비어 있음 |
| 쇼핑 구매→의류 import 연결 | 0건 | 승인 의류는 일반 업로드/등록 경로로 적재했으며 쇼핑 구매 이력으로 연결되지 않음 |
| 위치 관측 | 114건 | API QA 및 합성 시연 관측. 사용/착용 횟수와 다른 데이터 |
| 환경 reading | 65행 | 시연 합성 환경, 실측 센서 데이터 아님 |

쇼핑 Mock Provider는 코드의 구매 목록6항목/LIKED1항목을 반환한다. 구매6개 중에는 취소·반품·필수 정보 누락 항목도 포함되어 있다. **옷장에 연결된 TONYWACK 상품 목록을 구매 이력으로 반환하는 Provider가 아니다.** 현재 bulk-import는 새 의류와 import 연결만 만들며 이미지·위치·상태 초기화를 연결하지 않는다. 그대로 실행하면 이미지 없는 UNKNOWN 의류가 추가되어 옷장 화면을 채우지 못한다.

회의 권고: 기존 garment ID를 유지하고, 해당 상품을 참조하는 **DB 기반 시연 구매 목록**과 기존 `shopping_import` 매핑을 만든다. 상품 원본 정보/합성 주문/보유 의류 인스턴스를 구분하고, 구매 단위1개는 garment1개에 연결한다. 같은 구매의 재실행은 기존 garment를 반환한다. LIKED는 별도 구매 후보로 유지한다. 이미 있는76개를 새 구매 일괄등록으로 다시 생성하지 않는다. 공개 실제 쇼핑 API가 있는 것으로 가정하지 않는다.

로그 기간은 아직 미확정이며 아래30일은 권고안이다. 사용 로그는 김수진·최휘재 각각 실제 시연 의류 ID를 참조하는 일정 기간의 **명시적 합성 착용 완료 기록**으로 구성하는 방향을 권고한다. 최근 자주 입은 옷/오래 안 입은 옷을 구분하고 취소·미래 기록이 집계에 섞이지 않게 한다. DB에 이미 허용된 confirmation method `ADMIN_MOCK`로 합성 출처를 구분하고 고정 식별자로 재적재를 멱등하게 하는 격리 시연 fixture를 권고한다. 현재 공개 착용 기록 API는 `USER`/`SENSOR_VERIFIED`만 받으며 서비스는 USER만 허용하므로 ADMIN_MOCK를 그 API로 바로 전송할 수는 없다. fixture 적재와 공개 사용자 확인 API를 혼동하지 않는다. 프론트에서 ID 글자 합으로 만든 Mock 횟수는 DB 로그와 교체한다. 코디 확정→자동 착용 생성 금지 계약은 계속 유지한다.

기간·빈도·세탁/케어 이력까지 채울지는 회의 결정 후 구체화한다. 확인되지 않은 실제 사용자 이력으로 위장하지 않는다. 원본 사진은 확보된 공식 상품 사진을 쓰되 공개·상용 사용 권리 게이트는 별도다.

## 5. 오른쪽이 비고 의류가 떠 보이는 이유

실제 브라우저 합성 화면을 확인했다. 행거21개는 그대로 연결되어 있지만 **선반은 K1/K2/K3 단품3개만** 있다. 오른쪽 닫힌 서랍 내부는 투시하지 않고, 문제로 지적한 영역은 오른쪽 열린 선반이다.

| 에셋 | 현재 원본1672×941 좌표 `(x,y,w,h)` | 보이는 문제 |
|---|---|---|
| K1 | 1005,96,112,24 | 윗 선반 왼쪽 단품, 하단이 선반 바닥에 닿지 않음 |
| K2 | 1128,120,116,17 | 같은 선반 오른쪽 단품, 왼쪽과 높이/두께가 다름 |
| K3 | 1003,440,115,29 | 안쪽 아래 선반 단품, 바닥 접점과 그림자 부족 |

DB/Scene/프론트는 현재 이 좌표를 일관되게 사용한다. Signed URL 오류나 DB 로딩 누락 때문에 뜨는 것이 아니라 **샘플의 전체 이미지 좌표를 실제 빈 선반의 바닥 접점·적층 위치로 보정하지 않은 배치 결함**이다. 세 장을 호출했다는 테스트 통과는 이 접점과 빈 공간 품질을 검사하지 않았다. 단품은 17–29px 높이이고 좌우2묶음×각3벌의 형태를 이루지 않는다. PNG 자체를 확대·늘이기만 하면 원근/접힌 두께가 망가질 수 있다.

기존 승인 배치 보고 `wardrobe-visual-review/REVIEW.md`는 다음 규격이다.

- E, 거울 바로 오른쪽: 4선반 × 좌우2묶음 × 3벌 = 24자리.
- F, 오른쪽 끝: 7선반 × 좌우2묶음 × 3벌 = 42자리.
- 오른쪽 총66자리. D 왼쪽 아래6자리까지 포함하면 접힌72자리, 행거21과 합쳐 시각93자리.

이는 전체 자리 기준이며33개 후보 또는 기존52개와 같은 수량이 아니다. 이전 작업에서는 샘플3개를 전체 선반 완료로 확대하지 않고 미확정 상품 등록도 보류했지만, **승인된 전체 배치에 대한 상품·슬롯·개별 에셋 매핑을 아직 완성하지 않은 상태**다. 그 결과 화면이 비었다. 이번 보고서는 이를 승인 범위의 핑계나 환경 장애로 처리하지 않는다.

### 기존 승인 기준과 범위 변경 선택지

| 선택 | 장점 | 남는 문제 |
|---|---|---|
| A. 기존 원본 규격대로 전체 선반을 채운다 — 권고 | 승인 구조 유지, 가족 옷장 밀도와 찾기 시연 완성 | 오른쪽66/왼쪽6의 각 자리·상품·소유자 매핑, 추가 접힘 에셋과 필요한 상품 적재가 필요 |
| B. 기존 DB 수량 중심으로 일부 선반만 채운다 | 추가 데이터/에셋 범위를 줄일 수 있음 | 원본 밀도와 승인한 모든 선반 규격을 달성하지 못하므로 범위 변경 결정 필요 |
| C. 같은3장을 복제하거나 의류를 배경에 일괄 굽는다 | 빠른 시각 채우기 | DB↔의류1개↔슬롯1개의 동적 찾기/이동을 깨거나 가짜 수량을 만들므로 비권고 |

A는 이미 승인된 원본 규격을 이행하는 기본안이며 새 승인을 요구하는 안이 아니다. B로 줄일 때만 승인 범위 변경이 필요하다. 후속 실행 지시에서 확정할 대상은 각 자리의 상품 재사용·추가 목록이다.

A에서는 행거와 빈 배경을 유지하고, 각 선반의 실제 바닥 선을 기준으로 두 묶음의 하단·접힌 세 겹·원근·접촉 그림자·앞뒤 가림을 먼저 맞춘다. **개별 garment ID별 투명 에셋**을 유지해 이동 시 한 벌만 제거/복귀할 수 있게 한다. 위치·capacity·anchor를 그 구조에 맞추고, 각 의류의 상품 원본 사진과 표시 파생 PNG는 분리한다. 기존 상품 재사용을 우선하되 실제 의류 하나를 여러 자리로 복제하지 않는다.

현재 집계는 서로 중복되지 않는다: **표시24 + 내부 숨김32 + 외부 상자11 + 닫힌 소품/신발 서랍9 =76**. 참고 수량: 현재 표시24 → 원본 전체93은 추가 시각 자리69개다. 현재 숨김 내부32개를 모두 재사용하고 외부/닫힌 보관20개를 그대로 유지한다는 가정이라면 총113개가 필요해 신규 의류37개가 더 필요하다. 이는 **가정에 따른 산술이며 확정 적재량이 아니다.** 외부 보관 의류를 회수해 재사용하거나 상품 적합성이 달라지면 신규량도 달라진다. 데이터부터 무조건113개로 늘리지 않고 자리 매핑을 먼저 확정해야 한다.

## 6. 확정 지시와 회의에서 결정할 사항

| 안건 | 권고안 | 다른 선택과 영향 |
|---|---|---|
| 오늘의 홈 카드 | 실제 추천2–3개를 기존 카드 파이프라인으로 만들고 완료 PNG 재사용. T1을 홈 기본 후보로 제안 | T2/T3/T4 또는 사용자 선택 기본. 네 독립 템플릿은 유지 |
| 홈 사용 이력 | 이번 지시대로 홈에서 제거, 별도 기존 캘린더/이력 화면 유지 | 삭제할 대상은 UI이며 추천 입력 DB 로그는 유지 |
| 시연 사용 로그 | 양 프로필 최근30일 합성 기록, 추천 집계7일/보관90일 유지 | 90일 전체 기록 구성은 계절 분석 시연을 풍부하게 하지만 데이터 설계 범위 증가 |
| 쇼핑 데이터 | 승인 상품과 기존 garment를 잇는 DB 기반 합성 구매 목록/멱등 import | 상품 후보 목록만 보여주면 구매→보유 연결 시연은 계속 미완료 |
| 계절·관리 입력 | 초기 홈은 겨울 조건, 등록된 합성 환경과 로그를 같은 서버 입력으로 사용 | 현재 ALL 이력 보류 유지 시 로그 적재 전 추천0건이 정상 결과 |
| 관리 설명 | 먼저 의류·장소·근거가 연결된 서버 결과 UI 완성, LLM 설명은 별도 결정 | OpenAI 사용 시 인증/비용/실패 대안 필요. 이번에 호출/설정하지 않음 |
| 오른쪽 상품 목록 | 기존 승인 A 규격 유지, 각 자리의 기존 상품 재사용/추가 목록 확정 | B로 밀도를 줄이려면 별도 범위 변경 결정 |

회의 후 후속 지시에는 선택한 기본 템플릿, 합성 로그 기간, 전체 선반 범위 및 상품 재사용/추가 방향을 적으면 된다. 이 보고서에서 선택안을 확정하거나 제품 구현·DB 적재를 재개하지 않았다.
