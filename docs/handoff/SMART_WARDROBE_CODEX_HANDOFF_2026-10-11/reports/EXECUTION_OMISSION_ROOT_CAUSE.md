## 1. 핵심 결론

**확인한 산출물에는 계약 변경을 생활 데이터 작업과 검증 기대값으로 전파한 흔적이 없으며, 이후 재개 목록도 그 좁은 잔여 목록을 이어받았다.** 이는 누락이 지속된 작업상 경위다. 별도 절차가 전혀 없었는지나 작성자의 내부 동기를 기록만으로 확정하지 않는다.

생활 데이터는 단순히 생성하지 않은 수준을 넘어 검증 코드가 `wear == 0`을 정상 상태로 고정했다. 조명은 기존 “선택=점등” 구현을 재검토하지 않고 브라우저 테스트가 같은 가정을 정답으로 사용했다. 홈·VTON·카드는 각각의 경로 성공을 확인했으나, 진입점→중간 화면→복귀→결과물의 전체 액션 계약으로 관리하지 않았다. 카드 시각 미완료는 보고했지만, 그 외 생활 데이터/사용자 플로우 누락은 잔여 목록에 구체 작업으로 기록하지 않았다.

전체 완료를 거짓으로 선언한 기록은 확인되지 않는다. 이전 보고서들은 PARTIAL을 명시했다. 그러나 **PARTIAL의 이유와 다음 작업 목록이 실제 미완료 범위를 충분히 담지 못한 것**은 확인된다. 부분 완료 표시는 누락된 요구를 추적하는 작업 목록을 대신하지 못했다.

### 가장 직접적인 검증 오류: 전체 0건과 증가 0건의 혼동

`6f5b667`의 브라우저 테스트는 LIKED/VTON/카드가 실착 이력을 자동 생성하지 않는지 확인하며 `history.length == 0`을 사용했다. 이 부작용 금지 요구 자체는 맞다. 그러나 **시연 DB에 이미 착용 이력이 존재해도 해당 액션 전후 증가량은0이어야 한다**가 올바른 기준이다. 빈 초기 DB에서 전체0 검증은 유효하다. 그러나 이후 생활 이력이 필요한 시연에도 데이터 증적의 wear0 기대값을 유지해 확장과 충돌하게 됐다. DB wear 집계는 가구 범위, 브라우저 history는 로그인 사용자 API 범위이므로 두 수치를 동일한 집계로 취급하지 않는다. 둘 모두 기존 이력이 있는 조건의 전후 증가량 검증을 대신할 수는 없다.

현재 [scripts/remediation_evidence.py](../../../../scripts/remediation_evidence.py)에도 같은 wear0 기대가 남아 있다. 이 기록은 데이터 누락이 단순 실행 실패가 아니라 계획/검증 기준에까지 고정된 사례임을 보여준다. 다만 이 assert만으로 당시 생활 시드 작성이 중단된 내부 동기를 입증하지는 않는다.

### 작업 인계에서 잃어버린 것

`f9aeeb8`와 `0310a37` 체크포인트는 “착용0”을 사실로 적었다. 그런데 다음 작업 목록은 카드 시각 Gate/기존 hidden 위치 매핑에 집중했다. 원 계약 요구별로 완료/미완료가 하나씩 대응하지 않아, **알고 있던 미충족 상태가 재개해야 할 작업으로 전달되지 않았다.** 사용자 시각 검수 중단은 정당했지만, 복귀할 때 원 요구와 잔여 목록의 차집합을 계산하지 않은 것이 인계 문제다. 컨텍스트 압축이 실제로 특정 요구를 지웠다는 직접 증거는 없으므로 그것을 원인으로 확정하지 않는다.

## 4. 왜 통과 결과가 누락을 잡지 못했는가

- 테스트 기대값을 계약에서 독립적으로 도출하지 않고 당시 구현 경로에서 만들었다. “Scene 클릭=찾기”, “빈 생활 DB=안전한 자동 이력 방지”가 대표 사례다.
- 데이터 검증은 사진/해시/개수/위치/용량에 집중했다. 경험→당시Context→피드백→추천/관리 소비의 연결 여부는 완료 조건에 없었다.
- 기능별 성공을 기록했지만 출발점과 복귀점이 다른 사용자 플로우의 조합은 별도 사례로 만들지 않았다. 수동 추천 버튼을 누른 결과가 초기 홈 검증을 대신했다.
- 카드 저장·다운로드 검증과 Gate A/B는 구분해 보고했지만, 같은 수준의 분리가 홈·생활 데이터·찾기 액션에는 적용되지 않았다.
- 계약 검사 x-fsd-ids/해시는 문서 구조 정합성 검사다. 문서 요구와 브라우저 행동의 일치 여부까지 검증하는 것으로 확대 해석하면 안 된다.

따라서 “테스트를 더 많이 돌렸어야 했다”보다 **무엇을 통과라고 정의했는지를 고쳐야 한다**가 핵심이다.

## 5. 반복 방지를 위한 실행 계약·검증 체계 수정안

지금은 제안만 한다. 계약/코드/테스트 변경은 다음 승인 이후 수행한다.

1. **요구별 실행 원장:** 원 계약 조항/후속 승인→필요 데이터→구현 작업→사용자 액션→금지 부작용→검증→증적→잔여 상태를 한 행으로 연결한다. 단순 P3/P4라는 단계 이름이나 테스트 수로 완료를 대신하지 않는다.
2. **변경 전파 규칙:** 합성 허용 등 후속 계약이 들어오면 이전 계획/seed/assert/체크포인트에 영향이 있는 행을 먼저 갱신한다. 폐기된 “첫 적재 이력 없음”은 초기 단계로 한정하고, 시연 생활 데이터 구축 작업을 별도 미완료로 등록한다. 자동 카드 정책처럼 진짜 충돌은 변경안과 승인 근거를 남긴다.
3. **데이터 완료 기준:** 단순 수량뿐 아니라 생활 맥락·구매·케어·판단·실행의 FK/시각/출처/사용처를 검증한다. 합성 이력0을 완료 기대값으로 고정하지 않는다. 미확정 값을 임의로 채우지 않고 해당 scenario를 보류 상태로 기록한다.
4. **부작용 테스트 기준:** 전체 count0 대신 액션 전후 delta0. 기존 착용/구매 데이터가 있는 fixture에서도 조회·선택·VTON·카드·확정이 실착을 추가하지 않는지 확인한다. 실착 완료는 명시적 실행으로만 증가해야 한다.
5. **플로우 완료 기준:** 각 진입점(초기 홈/탐색/카드/내 옷)별 조회·선택·명시적 실행·성공/실패/취소·복귀를 검증한다. 선택 무점등과 찾기 점등을 별개 사례로 두고, 카드/Context/프로필/스크롤 보존을 확인한다.
6. **시각/파이프라인 분리:** 승인 전체 배치와 샘플 개수, 카드 A/B와 PNG C를 각각 다른 항목으로 유지한다. 부분 통과가 다른 항목을 자동 완료시키지 못하게 한다.
7. **재개 체크포인트:** 다음 작업은 원장의 모든 미완료/차단 행에서 생성한다. 미충족인데 다음 작업에도 없는 행은 인계 실패로 판정한다. 기존 계약 전체와 차이를 검토하기 전 새 국소 작업의 완료 보고로 종료하지 않는다.
8. **완료 보고:** 계약 필수 항목 전체가 완료되기 전 전체 완료 금지. PARTIAL 보고에는 각 미완료 요구 ID·원인·재개 작업·필요 승인·미검증 조건을 반드시 포함한다. “추가 작업은 카드와 외부 게이트”처럼 실제 누락 범위를 줄이는 보고를 방지한다.

권장 검증 흐름은 **확정 요구 원장→시연 데이터/연결 사전검증→행동별 양성·음성 테스트→엄마/아들 첫 진입부터 전체 시연→원본 시각 검수→원장 미완료0 여부 확인**이다. 기존 P3/P4→P7→P5/P8/P9→P10 순서는 유지한다.

## 6. 근거의 한계와 이번 작업 범위

Git의 실행 코드와 같은 시점의 체크포인트는 누락의 전파 과정을 뒷받침한다. 하지만 어떤 생각으로 일부 작업을 생략했는지, 중간 비기록 계획이 있었는지, 어느 컨텍스트 압축 시점에 항목을 잃었는지는 증명할 수 없다. 별도 “의도적인 축소 승인” 기록도 발견하지 못했다. 이 보고서의 결론은 개인 의도가 아니라 **요구 전파·완료 기대값·잔여 인계의 구조적 오류**에 한정한다.

이번에는 과거 커밋과 현재 문서를 읽었으며 제품 데이터 재조회/생성·API 실행·구현 변경을 하지 않았다. 보고서만 로컬 기록한다. 원격 push·배포 없음.
