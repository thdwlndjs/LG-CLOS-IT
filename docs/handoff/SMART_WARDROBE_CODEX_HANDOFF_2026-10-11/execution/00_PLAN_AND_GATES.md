## P3의 순서 해설

**실재 제품 검증과 원본 이미지 출처가 먼저이고, 물리 DB 적재는 그다음이다.** 다만 DB 관계 설계와 시드 스크립트 구조는 P0~P2에서 병행 설계할 수 있다. P3a 파생 이미지 전체를 완료하기 전이라도 승인된 source asset·item ID가 확정되면 **원본 이미지와 구조적 DB 적재**를 시작할 수 있다. 이후 파생 에셋은 item ID에 추가 연결한다. 즉, P3a→P3b를 절대 직렬로 고정하지 않는다.

## G1 체크: 사용자가 집에서 확인할 내용

1. 4인 가구 제안 수용 여부. 시연 배우는 엄마·아들 확정.
2. 35/8/8 제안 수량 또는 수정안, 물리 수납 좌표/선반 구획.
3. 실제 상품 후보·공식 제품 근거·이미지 권리·접근성/계절 역할.
4. 데이터/서비스 비용, Decart API 모드 지원, 원격 DB/운영 영향.
5. P3 스키마/시드 마이그레이션/백업/롤백 계획.

## 자동화 범위

- 지금 즉시 허용: 로컬 파일 탐색, 읽기, 문서/CSV 작성, 사용 가능한 웹 조사, 구조/위험/테스트 설계.
- 승인 후 허용: 로컬 격리된 데이터·에셋 생성/시험, 스키마 변경, 기능 구현.
- 별도 승인: 과금 발생 외부 API, 외부 서비스 업로드, 운영 DB 수정, 원격 push/merge, 실기기 제어, 개인정보 실사진 보존.
- 인터넷 접근이 막혀 제품 확인 못 하면 `blocked/unverified` 표시하고, 조사 불가를 추정/허위 데이터로 대체하지 않는다.

## Git 원칙

작업트리 보존 → 확인된 안전 작업 브랜치 사용(기존 브랜치 강제 변경 금지) → Conventional Commits `docs`, `feat`, `fix`, `refactor`, `test` → 단계별 독립 변경·테스트 → 무단 push/merge 금지. 문서 작업만 하는 첫 실행은 기존 Git 상태를 확인하고 기존 사용자의 미커밋 변경과 겹치지 않게 새 보고서만 작성.
