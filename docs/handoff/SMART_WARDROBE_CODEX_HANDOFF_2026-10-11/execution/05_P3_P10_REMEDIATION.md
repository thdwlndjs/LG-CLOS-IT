기존 `feat/handoff-p3-p10` 브랜치와 구현을 기반으로 진행하며, 완료된 코드를 불필요하게 재작성하지 마라.

\## 1. 기존 P3 데이터 구축의 범위 오류 시정



\### 1.1 수량 계약 재해석



기존 조사 후보 13개, 검증·적재 11개는 \*\*초기 기술 검증용 최소 데이터셋\*\*이다. 최종 시연 목표 수량이 아니다.



기존 설계 기준안은 다음과 같다.



| 구분 | 기준 수량 | 목적 |

|---|---:|---|

| 옷장 내부 의류 | 35개 | 디지털 트윈·위치 탐색·코디 추천 |

| 외부 보관 의류 | 8개 | 계절별 보관·회수·일괄 이동 |

| 소품 | 8개 | 코디 구성·카드 다양성 |

| \*\*합계\*\* | \*\*51개\*\* | \*\*최종 시연 기준 데이터셋\*\* |



51개는 기존 기준안이며 절대적인 제품 수량 제한은 아니다. 그러나 이번 시연 구축에서는 \*\*최소 51개 수준의 데이터셋 확보를 작업 목표로 삼는다.\*\*



카테고리·계절·소유자·위치별 구성이 실제 시연에 적합해야 하며, 단순히 수량만 채우지 마라.



엄마·아들을 중심으로 구성하되 4인 가족 데이터 모델을 유지한다.



\### 1.2 실제 상품 조사 확대



기존 PC01\~PC11을 재사용하고, 부족한 의류·소품을 추가 조사하라.



\- 실제 존재하는 브랜드·모델·색상·카테고리 기반

\- 무신사 정식 제휴를 가정한 상품·구매 내역 연동 구조 유지

\- 상품명·브랜드·이미지 출처·확인 URL 기록

\- 확인되지 않은 실제 상품 정보 생성 금지

\- 동일 상품의 색상·옵션을 별도 품목으로 사용할 경우 명확히 구분

\- PC12·PC13도 재조사하되 확인되지 않으면 대체 상품 탐색

\- 특정 후보가 막혀도 다른 상품을 찾아 목표 규모까지 조사 지속



\*\*13개 조사 후 11개 적재에서 종료한 기존 방식은 반복하지 마라.\*\*



실제 무신사 제휴나 소비자 구매 내역 API 지원이 확정된 것처럼 표시하지 마라.



\### 1.3 실제 이미지 확보



DB에 상품명만 존재하는 상태는 최종 적재 완료가 아니다.



시연에 필요한 이미지 에셋을 확보하고 다음을 연결하라.



\- 상품 대표 이미지

\- 옷장 표시용 의류 이미지

\- 가능한 경우 누끼·옷걸이·접힌 상태의 이미지

\- 코디 추천·코디카드에 사용할 의류 이미지

\- 에셋 원본 URL, 파일 해시, 변환 이력



외부 상품 이미지는 출처와 이용 조건을 기록하고, 현재 PoC와 향후 상용화 계약 조건을 구분한다.



실제 이미지가 확보되지 않은 경우 해당 품목을 최종 시각 검증 완료로 처리하지 마라. 다만 다른 검증 가능한 상품이나 허용된 데모 에셋을 탐색하여 작업을 계속 진행하라.

\## 2. 데모 데이터와 실제 측정 데이터의 경계 수정



기존 실행은 실측되지 않은 의류 위치를 임의 생성하지 않는다는 규칙에 따라 위치 연결을 0개로 유지했다.



그러나 \*\*데모 계정의 가상 의류 배치와 실제 센서 관측값은 서로 다른 개념\*\*이다.



다음 기준을 적용하라.



| 데이터 | 처리 원칙 |

|---|---|

| 물리적 옷장 구조·칸 좌표 | 제공된 옷장 이미지와 실제 측정 자료를 근거로 구성 |

| 데모 의류의 칸별 배치 | 확정된 슬롯 구조 내에서 합성 시연 데이터로 설계 가능 |

| 외부 보관함 배치 | 합성 시연 데이터로 구성 가능 |

| 착용 이력·세탁 상태 | 합성 데이터 허용 |

| 날씨·습도·캘린더 | 합성 데이터 허용 |

| 실제 센서 측정·LED 작동 | 검증하지 않았다면 실제 작동으로 주장 금지 |



사용자 화면에 별도의 `MOCK` 배지를 강제하지 않는다.



단, 테스트와 개발 문서에서는 합성 데이터와 실제 연동 결과를 식별할 수 있어야 한다.



\*\*시연용 의류 위치를 실제 관측이 아니라는 이유만으로 전부 UNKNOWN으로 남기지 마라.\*\*



단, 슬롯 자체의 위치·크기·수용량이 미확정이라면 이를 임의로 실측값처럼 확정하지 말고, 이미지 기반 측정이나 명시적인 데모 레이아웃으로 구분해 진행하라.

\## 3. P4 — 실제 옷장 화면 완성



기존 Scene API와 레이어 렌더링 구조를 유지한다.



다음 작업을 완료하라.



1\. 기존 옷장 원본 이미지와 관련 에셋을 재확인한다.

2\. clean plate 제작에 필요한 배경·의류·거울 영역을 분석한다.

3\. A\~G 슬롯의 위치·경계·anchor·가림 관계를 정의한다.

4\. 실제 DB 의류를 각 슬롯에 동적으로 배치한다.

5\. 옷장 내부·외부 보관 위치를 UI와 일치시킨다.

6\. 의류 선택·찾기·코디 확정 시 대응 슬롯을 강조한다.

7\. Mock LED 영역이 실제 화면 슬롯과 일치하는지 검증한다.



기존 이미지에 의류가 합성되어 있다면 이를 그대로 배경으로 사용해 중복 의류가 보이게 하지 마라.



\*\*인수 조건:\*\* 엄마·아들 계정에서 옷장에 등록된 의류가 실제로 표시되고, DB 위치 변경에 따라 화면도 갱신되어야 한다.

\## 4. P7 — 코디카드 원본 복원



현재 T1\~T4는 독립 scaffold와 PNG 생성 파이프라인만 구현된 상태다.



\*\*이를 원본 템플릿 복원 완료로 간주하지 마라.\*\*



기존 네 장의 참조 이미지를 기준으로 각각 별도 복원 작업을 수행한다.



\### Gate A — 원본 디자인 복원



\- 원본 배치·크기·회전·접힘 형태

\- 의류 간 가림·중첩 순서

\- 그림자·광원·질감

\- 배경·여백·장식 요소

\- 원본에서 분리 가능한 레이어와 복원해야 할 영역



원본 이미지의 시각적 특징을 단순한 텍스트 설명만으로 재구성하지 마라.



가능하면 이미지 기반 레이어 추출, 마스크, 좌표 측정, SVG/벡터·래스터 혼합 방식을 사용하고, 이를 React 렌더링 구조에 반영하라.



각 템플릿의 복원 전후 이미지를 나란히 비교하고 차이를 기록한다.



\### Gate B — 실제 의류 치환



복원된 각 템플릿에 DB에 등록된 의류 이미지를 치환한다.



\- 배치와 가림 구조 유지

\- 원본 템플릿의 스타일 유지

\- 의류 잘림·왜곡·배경 잔여물 확인

\- 서로 다른 4종의 템플릿 특성 유지



\### Gate C — 실제 PNG 생성



기존 React → Playwright → PNG → MinIO → DB 저장 경로를 활용한다.



\*\*8×8 파란색 합성 fixture로 PNG가 생성되는 것만으로 Gate A/B/C 전체 통과를 선언하지 마라.\*\*



최종 결과는 실제 의류 이미지가 들어간 T1\~T4 PNG와 원본 비교 증적으로 제출한다.

\## 5. P5·P6·P8 — 실제 데이터 기반 기능 완성



\### P5 — 홈 추천



\- 등록된 보유 의류로 2\~3개 코디 추천

\- 실제 의류 이미지 표시

\- 캐러셀 선택 상태 유지

\- `AI 입어보기` 진입

\- VTON 이후 이전 추천 상태로 복귀

\- 사용자 선택 시 코디카드 생성 연결



\### P6 — VTON



\- 보유 의류와 LIKED 상품 모두 VTON 입력 허용

\- LIKED는 자동 보유 의류 등록 금지

\- 기존 Mock 경로와 실제 Decart 경로 분리

\- API 키·비용 승인이 필요한 실제 호출은 별도 차단

\- 호출 없이 실제 VTON 성공으로 표시하지 않음



\### P8 — 보관·회수



\- 겨울철 계절 이동 시나리오 구현

\- 여름 의류 보관 제안

\- 겨울 의류 회수 제안

\- 간절기 의류는 기본적으로 유지

\- 사용자의 이동 승인과 실제 완료 분리

\- 완료 시 용량 재검사 및 DB 위치 갱신

\- 갱신된 위치를 디지털 트윈에 반영



데모 계정의 계절·착용·보관 데이터는 합성할 수 있다.

\## 6. P9 — 최종 E2E 시연 검증



다음 시나리오를 실제 브라우저에서 검증한다.



1\. 엄마 계정 로그인 및 가족 공유 옷장 조회

2\. 실제 이미지가 있는 의류의 옷장 배치 확인

3\. 자연어 또는 UI 기반 의류 찾기

4\. 대응 슬롯 표시 및 Mock LED 확인

5\. 겨울철 보관·회수 제안 확인

6\. 이동 승인 후 실제 완료 처리

7\. DB 위치 변경 및 옷장 화면 갱신 확인

8\. 실제 보유 의류 기반 코디 추천

9\. 보유 의류 또는 LIKED 상품 VTON 진입

10\. 추천 화면 복귀 및 코디 선택

11\. T1\~T4 중 선택한 템플릿으로 코디카드 생성

12\. PNG 저장·재조회·다운로드



각 단계에 대해 스크린샷·테스트 결과·미충족 조건을 기록하라.



외부 API나 실제 하드웨어가 필요한 단계는 Mock E2E와 실제 검증을 분리해 보고한다.

\## 7. 실행 및 중단 규칙



이번 작업은 \*\*기존 P3\~P10의 미완료 항목을 해결하는 후속 구현\*\*이다.



사용자에게 매 단계 승인을 요청하지 말고, 기존 G1 계약 범위 내에서 진행 가능한 작업은 계속 수행하라.



자료 부족 시에는 다음 순서로 대응한다.



1\. 기존 저장소·인계 패키지·참조 에셋 재탐색

2\. 추가 조사 또는 검증 가능한 대체 자료 확보

3\. 기존 구현을 재사용한 해결 방법 탐색

4\. 해결할 수 없는 외부 의존성만 BLOCKED 처리

5\. 독립적으로 가능한 나머지 작업 지속



금지 사항:



\- 운영 DB 변경

\- 원격 push·merge·배포

\- 승인 없는 유료 API 호출

\- 기존 팀원 작업물 강제 덮어쓰기

\- 상품 정보·이미지 출처·테스트 결과 조작

\- 실제 연동 성공을 Mock 결과로 대체하여 보고



로컬 브랜치·커밋·격리 DB 사용은 허용한다.
