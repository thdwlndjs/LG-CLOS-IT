# Smart Wardrobe PoC — A단계 계약 정합화 지시서

## 목적
기존 설계·계약과 최신 사용자 확정 사항의 충돌을 해소하고, B~G 단계의 구현 기준을 문서로 고정한다. **A단계는 문서 작업만 수행한다.** 코드, DB, 에셋, 실행 설정을 변경하거나 마이그레이션·시드·생성 API를 실행하지 않는다.

## 기준 자료
1. `docs/handoff/SMART_WARDROBE_CODEX_HANDOFF_2026-10-11/reports/POC_IMPLEMENTATION_STATUS_AUDIT.md`
2. 프로젝트 내 MASTER, FSD, OpenAPI, 기존 단계별 계약 및 승인 기록
3. 아래 '최신 확정 정책'. 충돌 시 최신 확정 정책을 우선하되, 이전 계약의 충돌 지점과 변경 사유를 명시한다.

## 최신 확정 정책

### 1. 의류 데이터·옷장
- 기존 보유 의류 76벌과 승인된 왼쪽 행거 배치를 보존한다.
- 오른쪽 선반은 승인 원본 이미지의 배치·밀도를 복원한다. 접힌 의류는 각각 고유 `garment_id`와 대응하고, 보관 위치는 칸 단위로 관리한다. 오른쪽 선반의 현재 떠 있는 옷·세 개만 보이는 상태·과도한 빈 공간을 복구 대상으로 명시한다. 왼쪽 행거 재설계는 범위 밖이다.
- 관심 의류(LIKED)는 사용자별 시연 데이터를 DB에 **사전 적재**한다. 보유 의류와 데이터·ID를 분리한다. 외부 쇼핑몰 API, 계정 연결, 구매 동기화 및 실제 결제는 구현하지 않는다.

### 2. VTON
- 보유 의류만, 관심 의류만, 혼합 조합 모두 동일한 의류 선택·시착 흐름에서 허용한다. 선택한 모든 의류가 실제 시착 입력에 포함되어야 한다.
- 의류 선택·변경만으로 VTON을 실행하지 않는다. 사용자가 `입어보기`를 눌러야 실행·결과 갱신된다.
- 생성 중 의류 선택은 허용하되 중복 `입어보기` 요청은 방지한다. 결과는 요청 시점의 의류 스냅샷에 대응한다.
- VTON 화면을 떠나면 임시 선택·시착 결과를 초기화한다. 늦게 도착한 결과가 재진입 화면을 오염시키지 않도록 한다.
- 코디 확정·코디카드 만들기 버튼은 관심 의류가 포함돼도 **숨기지 않는다**. 실행 시 보유 의류만 지원한다는 안내를 제공하고 부작용을 발생시키지 않는다.

### 3. 코디 확정·착용 이력·LED
- 이번 PoC에서 **보유 의류만으로 구성된 코디의 `코디 확정`은 착용한 것으로 간주**한다. 별도의 실제 착용 확인·평가 단계는 만들지 않는다.
- 코디 확정 성공 시 해당 사용자·코디·시각·맥락의 착용 이력을 **정확히 1회** 기록하고, 알려진 내부 보관 칸의 LED를 동시에 점등한다. 같은 칸은 중복 점등하지 않는다.
- LED는 30초 후 자동 소등한다. 재호출 시 30초 타이머를 갱신한다. 단순 의류 선택은 LED를 켜지 않는다. `내 옷 찾기`에서도 30초 점등을 적용한다.
- 외부 보관·위치 불명 의류는 점등할 수 없음을 안내하되, 위치가 알려진 다른 의류의 점등은 수행한다. 외부 보관함 LED 연동은 제외한다.
- 코디카드 저장은 착용 이력을 만들지 않는다. 저장 카드에서 `이 코디 입기`를 실행하면 그 시점의 새 착용 이력을 기록한다.

### 4. 홈 추천·관리
- 사용자별·일자별 최초 홈 방문 시 맥락에 근거한 코디 PNG 2~3개를 준비하고 당일 재사용한다. 자동 생성되는 것은 **홈 추천 미리보기**이며, 사용자의 저장 코디 갤러리에 자동 저장하지 않는다.
- 날씨·일정·착용 이력·보유 의류를 근거로 추천한다. 사용자별 시연 이력과 맥락은 데이터로 준비하되 실제 데이터와 시연 데이터를 내부적으로 구분한다.
- 홈에는 최우선 보관·회수 관리 제안 1개만 표시한다. 우선순위는 다가오는 일정의 회수 > 계절별 보관·회수 > 장기 미착용 의류이다. 전체 목록은 관리 화면에서 제공한다.
- 관리 제안의 수락은 위치를 변경하지 않는다. 사용자가 `이동 완료`를 실행한 시점에만 DB 위치를 변경한다. 진행 중 화면 이탈 시 미완료 작업은 취소하고 제안은 유지한다.
- 특별 관리 의류는 소재·케어라벨에 따른 가이드·권장 주기만 제공한다. 실제 케어 완료를 임의 생성하지 않는다.

### 5. 코디카드·공유
- 보유 의류만으로 구성된 코디에서만 T1~T4 중 템플릿을 명시적으로 선택하여 PNG를 생성·저장할 수 있다. 의류 변경만으로 자동 생성하지 않는다.
- 네 템플릿은 서로 다른 접힘·배치 특성을 보존해야 하며 단순히 같은 레이아웃의 변형으로 간주하지 않는다. 시각적 원본 일치 검증을 별도 게이트로 둔다.
- 저장 카드의 조회·재시착·공유 UI·삭제를 지원한다. 공유는 SNS 공유 시트 목업과 실제 PNG 저장/다운로드를 포함하며 SNS 게시 성공을 가장하지 않는다.
- 카드 저장과 코디 확정은 독립 동작이다.

## 계약 정합화 작업
1. 기존 MASTER/FSD/OpenAPI/단계별 계약에서 위 정책과 충돌하는 모든 조항을 찾아 **기존 문구 → 최신 문구 → 영향받는 API·DB·UI·테스트** 형태로 변경표를 작성한다.
2. 권위 있는 기준 문서와 변경 대상 문서를 지정하고, 문서 간 상충을 해소한다. 단, 승인된 범위 외 기존 정책을 임의 변경하지 않는다.
3. 각 요구사항에 고유 ID, 입력/상태, 허용 동작, 금지 부작용, 테스트 시나리오 및 완료 판정을 연결한다.
4. B~G 단계의 의존성·작업 범위·검증 게이트를 작성한다. **단계마다 구현 → 독립 검증 → 증적 제출 → 사용자 승인 → 다음 단계** 순서를 강제한다.
5. 원본 이미지, 현재 데이터, 기존 실행 증적의 경로를 확인하여 링크한다. 찾지 못한 자료는 추측하지 않고 `확인 필요`로 표시한다.

## 필수 산출물
- 계약 변경 이력 및 충돌 해결표
- 최신 요구사항 추적표(요구사항 ID ↔ 문서 ↔ 코드 영향 범위 ↔ 테스트)
- B~G 단계별 실행 계약 초안과 승인 게이트
- 미해결 질문 목록(실제 구현을 막는 항목만)

## 완료·중단 조건
- 이번 단계에서 **코드·DB·에셋·환경설정 수정 및 구현 실행 금지**.
- 변경 전후 diff와 변경 파일 목록, 아직 충돌하는 항목을 보고한다.
- 계약이 명확하지 않은 지점은 임의로 확정하지 말고 질문한다.
- A단계 문서 작업 후 **반드시 중단**한다. 사용자 명시적 승인 없이는 B단계로 진행하지 않는다.
