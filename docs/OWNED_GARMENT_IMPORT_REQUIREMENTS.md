# 실제 보유 의류 적재 요구사항

기준일: 2026-10-09. 상태: **요구사항 정리 완료, 대상 계정·기기·수량·이미지 처리 확인 대기, 실제 적재 미실행**.

요청 해석: 검증된 통합 구현을 Git에 저장하고, 실제 보유 의류 적재의 계약과 입력을 먼저 정리한 후 확인된 실물만 기존 등록 API로 적재한다. 통합 테스트의 합성 구매 내역을 실제 사용자 데이터로 복사하지 않는다.

## 기준과 문서 대조

이번 실제 보유 URL 적재의 실행 기준은 이 문서다. 제품의 쇼핑 UI 정책은 [통합 결정 11](11_INTEGRATION_DECISIONS_v1.2.md), [계약 충돌 검토 14](14_CONTRACT_CONFLICT_REVIEW_v0.2.md)를 유지하며, 구현 상태는 [통합 구현 보고서](INTEGRATION_IMPLEMENTATION_REPORT.md)와 실행 `/openapi.json`, Migration 0004를 따른다. 원본 설계와 전달 자료는 수정하지 않는다.

| 자료 | 차이 또는 역할 | 적용 |
|---|---|---|
| 로컬 비공개 `OWNED_GARMENT_IMPORT_REVIEW.md` | URL별 추출 근거. 통합 전에는 name/device API 매핑 없음 | 상품 식별 근거로 유지하고 최신 DTO 매핑은 본 문서를 사용 |
| `integration_sources/10_DB_IMPORT_AND_SHOPPING_INTEGRATION_DESIGN.md` | 카탈로그·variant 모델 및 선택 가져오기 제안, 개인 상품 목록 포함 | 제안은 확정 정책이 아님. 개인 목록은 Git 제외. 원본 유지 |
| 쇼핑 변경요청 09 | 이전 관심 유형과 선택 가져오기 제안 | 최신 11·14의 LIKED 전용·구매 일괄 등록 정책 우선 |
| 최신 결정 11·14 | 브랜드/사이즈 추가 금지, 과설계 제거, 실패 항목 분리 | 신규 필드·카탈로그 Migration 없이 기존 의류 API 사용 |
| `backend/app/schemas/sprint1.py` | 선택 name/device_id 지원, category/color 필수 | 상품명은 name에 매핑. brand/size/attributes/source_url 요청 금지 |

실제 보유 URL 목록과 Mock PURCHASED 목록은 서로 다른 입력이다. URL 목록을 구매 증빙·LIKED 기록으로 변환하거나 Mock Provider fixture에 넣지 않는다. 최신 구매 일괄 등록 정책이 사용자 제공 URL의 미확인 소유자·색상·수량을 자동으로 채우는 근거는 아니다.

## 데이터 매핑

| 입력 | API/보존 위치 | 규칙 |
|---|---|---|
| 대상 사용자·물리 옷장 | owner_id, device_id | 사용자가 지정한 실제 회원·접근 가능한 기기. household/owner 유지. Seed 데모 계정 자동 선택 금지 |
| 상품명 | 선택 name, 최대 200자 | 확인된 원문 사용. 초과 시 임의 절단하지 않고 검토 |
| 카테고리·색상 | 필수 category, color | 근거가 있는 정규화만 적용. 선택 옵션 미확인은 보류 |
| 소재·케어 | 선택 material, care_label | 검증된 값만 전달. 미확인은 null 또는 생략. 카테고리로 소재 추정 금지 |
| 상품 이미지 | 선택 image_asset_id | GARMENT upload intent → 서명 PUT → SHA256 finalize → READY 확인 |
| 브랜드·원본 URL·상품번호·원문·추출 근거 | 비공개 `data/imports/` 원장 | API 필드에 숨겨 넣지 않음. 보유 의류와 원본 상품 분리, garment_id로 연결 |
| 보유 수량·사이즈 | 비공개 보유 개체 원장 | 수량 확인 후 한 실물당 garment 1개. 모델 착용 사이즈를 복사하지 않음 |
| 위치·태그·관측·착용·세탁 | 확인 전 생성하지 않음 | location/tag null, 공유·계절 빈 목록. 신규 상태는 서버 기본 UNKNOWN 유지 |

상품 사진은 `CATALOG_REFERENCE`, 실제 보유 의류 촬영 사진은 별도 출처로 표시한다. 상품 사진을 사용자의 실물 상태·위치 증거로 취급하지 않는다. 상품 메타데이터를 DB 내부에서 모두 조회하는 별도 카탈로그 기능은 이번 최소 적재 범위에 포함하지 않는다. 원장이 로컬 파일이므로 다른 PC로 이동할 때 안전한 비공개 전달이 필요하며, DB만으로 원본을 복구할 수 있다고 주장하지 않는다.

## 확인된 입력과 보류

이전 조사 기록은 입력 10개, 고유 주소 9개다. 기본 등록 후보 4개, 상품 식별 충돌·색상 누락·본문 추출 실패가 있는 나머지 입력은 보류다. 후보라고 해서 최신 이미지 다운로드와 등록까지 성공한 것은 아니다. 개인 URL·상품명·항목별 근거는 비공개 검토서에만 보관한다.

실제 실행에 필요한 입력:

1. 대상 계정과 device_id, 기존 데이터와 중복된 보유 의류 여부.
2. 후보별 실제 수량과 등록 대상 목록. 같은 최종 URL은 하나로 묶되, 두 벌 확인 시 개체를 분리한다.
3. 상품 식별 충돌의 올바른 의류, 옵션 색상, 추출 실패 항목의 검증 가능한 정보. 답이 없는 항목은 계속 보류한다.
4. 이미지 포함 여부 및 대상 계정의 기존 image_upload_consent. 실행 지시만으로 동의 값을 변경하지 않는다.

이미지 포함 대상으로 정한 항목의 다운로드·검증·업로드 실패 시 그 항목을 성공 처리하지 않는다. 이미지 없는 등록은 사용자가 해당 방식을 지정한 경우에만 진행한다. 누락·보류·실패 항목을 결과에서 숨기지 않는다.

## 실행·중복 방지·검증

1. 소유자·기기·기존 의류를 읽고, 최신 상품 식별과 이미지 검증 결과를 비공개 계획 JSON에 고정한다. 네트워크 차단 또는 본문 실패 시 다른 상품으로 대체하지 않는다.
2. 실물 키 규칙 버전은 v1로 고정한다. 출처 키는 `MUSINSA:<상품번호>`, `TONYWACK:<상품번호>`, `LMOOD:<상품번호>`이며 URL의 추적 파라미터·화면 경로는 식별 키에 넣지 않는다. 옵션은 확인된 색상 및 제공된 경우에만 보유 사이즈를 정렬된 JSON으로 고정한다. 대상 owner/device + 출처 키 + 옵션 JSON + 실물 순번을 고정 직렬화하고 SHA256으로 원장 키를 만든다. 순번은 확인된 수량의 1..N을 처음 계획에서 배정한 후 재번호 부여하지 않는다. 추가 개체는 기존 최대 순번 뒤에 붙인다. 같은 옵션의 여러 벌은 사용자 확인을 통해 구분하며 기존 Seed와의 매칭도 자동 추측하지 않는다.
3. 실행 전 원장을 디스크에 원자적으로 기록하고, 각 실물의 고정 요청·Idempotency-Key·업로드 단계·asset_id·garment_id·응답을 보존한다. 실행 원장에 대한 단일 실행 잠금으로 동시 실행을 차단한다. 인증 토큰·비밀번호·서명 URL은 원장에 저장하지 않는다.
4. 이미지 동의와 READY 자산을 확인한 뒤 개인 계정의 기존 POST /api/v1/garments를 사용한다. 직접 INSERT 및 임의 상태 보정 금지.
5. 실제 구현 `application/common/idempotency.py`와 garment 등록 서비스는 응답과 변경을 같은 트랜잭션에 저장하며, 같은 키·같은 본문을 재실행하지 않는다. 기본 유효기간은 86400초(24시간), 본문 변경 또는 만료 키는 409다. 불확실한 응답은 유효기간 내 같은 키·같은 본문으로 재조회/재시도한다. 만료 또는 멱등 기록 삭제 후의 미확정 실행은 새 키로 자동 재등록하지 않고 검토한다. 다른 키로 재실행하더라도 원장의 이미 완료된 실물은 건너뛴다. 원장이 없는 기존 실물은 사용자 중복 확인이 필요하다.
6. 의류 목록/상세와 DB를 다시 읽어 owner/device/name/category/color/READY 이미지가 계획과 일치하는지 확인한다. 최소 권한 DB 읽기는 증적 확인용이며 API 쓰기를 우회하지 않는다.
7. 동일 계획 재실행 시 신규 garment 0개, 개수 증가 0개인지 확인한다. 화면 재조회, 비공개 이미지 GET, 등록 결과·보류·실패 건수 및 착용·세탁·관측 이력 증가 0을 검증한다.

전체 요청 완료는 원래 입력 10개의 각 항목이 등록·확인된 중복/대상 제외 등 최종 결과로 정리되고 모든 등록 대상의 조회·이미지(포함 대상으로 정한 경우)·재실행 멱등 검증이 통과한 경우에만 판정한다. 후보 일부만 확정해 실행하면 해당 부분의 단계 완료이며, 보류 항목이 남은 전체 요청은 미완료다. 현재 DB에 실제 상품 목록을 적재했다는 증거는 없으며 기존 개발용 Seed 의류 3건을 유지한다.

## Git 및 재현

공개 가능한 구현 코드·정책 문서·UI 자산만 커밋한다. `.env`, 인증정보, 원본 팀원 전달 묶음, 개인 상품 목록·적재 원장, 백업·스크린샷·테스트 로그는 제외한다. 재현에 필요한 팀원 UI 실행 코드는 `web/src/mirror/`, 시각 자산은 `web/public/`에 포함한다. 원본과 90개 시각 소스 비교는 로컬 전달 묶음이 있는 환경에서만 가능하다.

적재 전 Git 선행 조건은 검증된 통합 변경이 `origin/main`에 반영된 상태다. 실행 원장에 `git rev-parse HEAD`와 원격 확인 시각을 기록하고 `git rev-parse origin/main`과 일치하는지 확인한다. `.env`와 비공개 원장을 제외한 실제 적재 코드·계약의 미커밋 변경이 있으면 먼저 검증·저장한다.

통합 실행·테스트 명령은 [통합 구현 보고서의 로컬 실행과 재현](INTEGRATION_IMPLEMENTATION_REPORT.md#로컬-실행과-재현)을 따른다. 실제 적재 실행 명령과 결과 원장은 대상 입력 및 이미지 처리 확정 후 마련한다. 현재 단계에서 DB·MinIO에 실제 보유 상품을 추가하거나 이미지 동의를 변경하지 않았다.
